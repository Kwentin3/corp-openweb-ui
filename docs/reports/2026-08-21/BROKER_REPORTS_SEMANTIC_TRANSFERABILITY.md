# Transferability of the Semantic Compiler

Дата: 2026-08-21

Статус: research-only, production не изменён

Verdict: `BROKER_SOURCE_DIALECT_NEEDS_RETHINKING`

## Коротко

Идея остаётся правильной:

```text
Canonical
→ маленькие закрытые смысловые решения
→ детерминированная сборка
→ typed projection
```

Но текущая форма `BrokerSourceDialect_v0` оказалась слишком узкой для новых
реальных отчётов. Проблема уже не в том, что LLM плохо читает числа. Canonical
сохранил клетки и адреса. Проблема в том, что наш контракт не умеет естественно
выразить то, что источник действительно сообщает.

На новых документах встретились:

- две разные валютные колонки в одной таблице;
- две разные комиссии в одной строке;
- две разные даты расчёта;
- РЕПО, внешне похожее на покупку/продажу, но не являющееся обычной сделкой с
  переходом владения;
- денежный журнал, где в одной физической таблице смешаны купоны, налог,
  комиссии, вводы и выводы;
- одна сделка, показанная источником в двух самостоятельных разделах — как
  заключённая и как завершённая.

Текущий dialect требует одну колонку на одну semantic role и делит residual по
типу всей таблицы. На этом реальный источник не помещается в контракт без
искажения смысла.

## Что проверено

Holdout был выбран до смысловых вызовов модели:

- тот же брокер, другой год — 2 отчёта;
- другой брокер — 1 отчёт;
- всего 38 страниц;
- development Canonical с root `bbf20e4e...` исключён.

Через текущий locator и текущих владельцев Canonical собрано:

| Проверка | Результат |
| --- | ---: |
| документов | 3 |
| страниц / locator calls | 38 / 38 |
| Canonical tables | 48 |
| structural chunks | 76 |
| адресуемых targets | 14 270 |
| потерянных targets | 0 |
| технически продублированных targets | 0 |
| legacy fallback | не использовался |
| production | не менялся |

Смысловой stand выполнил ровно 9 заранее запланированных вызовов: по три для
H3, H6 и H8. Retry, repair и best-of-N отсутствовали. Первый H3 был отклонён
валидатором до сохранения raw response; повторный вызов вместо него не делался.

## Фактический результат

### H3 — схема таблицы

Все 3 ответа были отклонены строгим контрактом из-за повторной semantic role.
Это не случайная галлюцинация:

- в двух сохранённых ответах модель одинаково увидела обычную таблицу сделок;
- в обоих она правильно оставила таблицу РЕПО как `UNMAPPED`;
- в реальной таблице сделок действительно есть две валюты, две комиссии и две
  даты расчёта;
- наш validator запрещает повтор одной role, поэтому корректная структура не
  помещается в dialect;
- между двумя доступными raw mappings разошлась только одна колонка: валюта
  цены была один раз `currency`, другой раз `unmapped`.

Вывод: H3 распознаёт общий смысл таблиц, но текущая модель ролей ошибочно
предполагает `one role → one column`.

### H6 — направление сделки

`3/3 exact`. Модель трижды выбрала тот же source ref покупки, а код однозначно
восстановил второе значение как продажу.

Это переносимая часть pattern: маленькое закрытое решение над уникальным
значением, а не row-level извлечение.

### H8 — residual денежного журнала

Все три запуска дали один и тот же ответ, но только `1/3` решений совпало с
независимой truth:

- комиссия распознана правильно;
- купон и налог были помечены `NOT_RELEVANT`;
- truth требовала `UNMAPPED`, потому что это релевантные source observations,
  которые текущий закрытый каталог `CASH_OPERATIONS` не умеет выразить.

Это стабильная, но опасная ошибка. Причина — не свободный текст сам по себе, а
ложное предположение, что одна физическая таблица содержит только один класс
экономических событий.

### Конечная projection

Projection hash повторился `3/3`, source accounting составил `24/24`, но все 24
выбранные записи остались `UNMAPPED` и typed records не появились.

Повторяемость доказана только для безопасной остановки. Это не доказательство
рабочего результата для Gate 5.

## Ответы на вопросы GOAL

### 1. Переживает ли подход новый документ?

Частично. Canonical, адресация, H6 и детерминированная сборка пережили новые
документы. Полный путь до runtime-ready projection — нет: его остановили
multi-page lineage и недостаточный dialect.

### 2. Что именно переносится?

Переносится task-form:

```text
маленькое schema/value decision
+ копирование значений кодом
+ строгий validator
```

Не переносится текущий набор предположений: уникальная role в таблице,
единственный смысл физической таблицы и три закрытых table types.

### 3. Как часто нужна LLM?

Для 15 проверенных строк обычных сделок row-level LLM не нужна: после доказанной
схемы все значения можно копировать кодом.

В денежном журнале другого брокера найдено 122 строки, но только 8 уникальных
source operation literals. Значит, следующий разумный контракт — одно закрытое
решение на новый literal/fingerprint и reuse, а не 122 row-level inference.

### 4. Работает ли reuse?

Механика работает:

- exact copy даёт тот же fingerprint;
- перестановка колонок меняет fingerprint и запрещает reuse;
- таблица РЕПО двух разных лет одного брокера дала одинаковый exact structural
  fingerprint; безопасный `UNMAPPED` mapping можно переиспользовать.

Reuse пока доказан только для exact структуры. Approximate reuse не разрешён.

### 5. Не превращается ли reuse в broker profiles?

Не должен. Ключ reuse — версия контракта плюс exact structural fingerprint, а
не брокер, год или имя файла. Ни один broker profile в stand не создан.

Если для переноса потребуются правила вида `broker/year/special case`, это будет
сигнал остановиться, а не расширять каталог исключений.

### 6. Стабилен ли результат?

- H6: `3/3 exact`;
- H8: `3/3 одинаково`, но семантически только `1/3` верно;
- H3: `0/3 validated`; два сохранённых raw outputs почти одинаковы;
- final projection: один hash `3/3`, но `0` typed records.

Стабильность без полезного результата не считается успехом.

### 7. Сохраняется ли source truth?

Да на физической границе: 14 270 targets, `lost=0`, technical duplicates `=0`.
Модель не переносила числа и не создавала source literals. Неизвестное не было
насильно материализовано.

Но `NOT_RELEVANT` для купона и налога показывает semantic-loss риск: релевантное,
которое dialect не знает, должно быть `UNMAPPED`, а не исчезать как нерелевантное.

### 8. Что происходит с дублями?

В одном новом отчёте найдено 133 группы полностью одинаковых строк, всего 266
observations. Ручной аудит контекста показал, что это не повтор обработки:
источник показывает сделки в разных разделах, например «заключённые» и
«завершённые». Canonical identities у них разные, technical target duplicates
равны нулю.

По одинаковым значениям дедуплицировать нельзя. Нужно сохранить обе source
observations и связывать их только по явно указанному source trade ID и смыслу
раздела. Текущий dialect не хранит этот observation context достаточно явно.

### 9. Хватает ли projection Gate 5?

Нет. В выбранном end-to-end срезе source содержит даты, инструменты, количество,
суммы, валюты и комиссии, но текущий compiler выпустил `0` typed records.

Причины разделены:

- source data присутствует;
- Canonical её сохранил;
- H3 понимает общий тип таблицы;
- `BrokerSourceDialect_v0` не выражает повторяющиеся роли и observation context;
- continuation не имеет доказанного logical-table lineage;
- поэтому validator правильно остановил materialization.

### 10. Правильно ли устроен BrokerSourceDialect?

Нет. Минимальная корректировка — не добавлять ещё один broker profile, а заменить
плоскую уникальную role на source-shaped поле:

```text
semantic_role + source_qualifier + source_ref
```

Например, две валюты остаются двумя наблюдениями с разными source qualifiers, а
не конкурируют за единственный `currency`. Аналогично для комиссий и дат.

Также projection должна сохранять:

- source section / observation kind;
- explicit source event key, если он есть;
- связь частей multi-page таблицы отдельным lineage sidecar;
- `UNMAPPED` как нормальное терминальное состояние.

Canonical при этом не меняется.

### 11. Какие реальные неопределённости остались?

Фактический небольшой список:

- является ли следующая таблица продолжением предыдущей;
- какой qualifier имеет повторяющаяся колонка одного общего смысла;
- РЕПО это или обычная покупка/продажа;
- что означает новый source operation literal;
- какую observation perspective задаёт раздел отчёта;
- что выражает остаточный free text: комиссия, купон, налог или неизвестное.

Числа, даты и обычные значения из доказанных колонок LLM выбирать не должна.

### 12. Где система должна останавливаться?

Fail-closed обязателен, когда:

- continuation lineage не доказан;
- fingerprint изменился;
- повторяющаяся role не имеет source qualifier;
- table/operation type отсутствует в контракте;
- source observation нельзя отличить от другого раздела;
- модель вернула duplicate role в старый уникальный контракт;
- релевантный смысл не помещается в catalog.

Последний случай должен завершаться `UNMAPPED`, не `NOT_RELEVANT`.

## Почему это не новый велосипед

Наблюдение совпадает с практикой document AI:

- Google прямо предупреждает, что PDF-таблицы на нескольких страницах могут
  быть разделены на две таблицы, и отдельно подчёркивает необходимость
  layout-aware chunks с унаследованным контекстом
  ([Google Document AI](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk)).
- AWS для multi-page tables разделяет `MERGE` и `LINK`: `LINK` сохраняет
  геометрию, а объединение может её исказить. Перед связыванием проверяются
  page context, число колонок, headers и margins
  ([AWS multi-page table handling](https://aws.amazon.com/blogs/machine-learning/postprocessing-with-amazon-textract-multi-page-table-handling/)).
- Сам table contract Textract хранит cells, merged cells, title/footer и явные
  отношения между блоками, то есть структура и связи являются отдельными
  сущностями
  ([Amazon Textract tables](https://docs.aws.amazon.com/textract/latest/dg/how-it-works-tables.html)).
- Docling также держит hierarchy, layout и provenance внутри единой document
  representation, не смешивая их с downstream business semantics
  ([DoclingDocument](https://docling-project.github.io/docling/concepts/docling_document/)).

Это поддерживает наш следующий шаг: не сливать страницы и не мутировать
Canonical, а добавить доказательный logical-table lineage и затем компилировать
source-shaped observations.

## Следующий разрешённый GOAL

Production пока не включать. Следующий узкий GOAL:

1. определить `BrokerObservationDialect_v1` только из обнаруженных потребностей:
   repeated role + qualifier, section kind, explicit source event key;
2. добавить отдельный immutable logical-table lineage sidecar с режимом `LINK`,
   а не физическим merge;
3. заменить row-level H8 для категориальных журналов на mapping уникальных source
   literals с exact fingerprint reuse;
4. пересчитать сохранённые raw H3/H6/H8 без новых provider calls;
5. доказать на том же holdout: полезные typed records, отсутствие двойного учёта,
   полный provenance и один final hash.

Никакой broker-specific профиль для этого не нужен. Если этот маленький v1 не
поместит оба источника естественно, pattern надо признать corpus-specific и не
интегрировать.
