# Коммерческое предложение из заметки: продуктовая проверка моделей

Дата: 23.10.2026. Рабочая версия: OpenWebUI 0.12.2, OfficeCLI 1.0.152.
Это продолжение [аудита подключения](office-model-coverage.report.md), а не
повторное предъявление внедрения OfficeCLI.

## Задание и источник

В исходном чате просили Word-файл, но получили заметку с инструкцией ручного
копирования. Отсутствующий `deepseek-flash` в Valves уже исправлен в PR #573.
Та проверка подтверждала другой, короткий синтетический сценарий; она не
создавала файл из полной заметки в исходном чате.

Новая проверка требует готовый скачиваемый DOCX из всего сохранённого текста:
12 разделов, четыре таблицы, поля `{{...}}`, пояснения и чек-лист. Запрещены
сокращение, переформулирование и добавление коммерческих условий. Markdown
должен стать заголовками, списками и таблицами Word. Финальные файл и ссылку
нужно получить в обычном Web UI.

Источник содержит 4824 символа и 145 текстовых блоков Markdown. SHA-256 UTF-8:
`c592c26684dace9289ca415de6e1fda557c37c53d274906a262ff6f8aec6641c`.
Перед внешними запросами окончательный запрос и штатная схема
`create_office_document` проверены на этом полном тексте. Существующая команда
`add /body`, `type: markdown`, `props.markdown` принимает его одним batch-item;
тот же нативный импорт уже используется операцией `export_answer_to_word`.
Новый генератор, клиент провайдера или владелец истории не создавались.

Исходный чат продолжен под его владельцем. Для обычного аккаунта создана
приватная копия той же общей заметки с пустыми полями, без бизнес-данных.
Побайтовое совпадение текста проверено до прогона. Все обычные модели получают
одинаковый естественный запрос в отдельных новых чатах; технические подсказки
в продолжении учитываются отдельно.

## Что считается подтверждением

- Считать native chat history, tool receipts и последний `result_file_id`.
- Скачать сам пакет DOCX и проверить полный порядок текста, все 145 блоков,
  отсутствие пропусков, повторов и добавленных слов; отдельно сравнить каждую
  ячейку четырёх таблиц с источником. Проверять `w:br`/табуляцию как разделители.
- Учитывать оформление `[ ]` символом `☐` отдельно от строгого равенства текста.
  Это не разрешение на другие изменения.
- Просмотреть рендер, привязанный к конечному File ID, включая все страницы.
- Скачать финальную ссылку кликом в браузере под тем же пользователем;
  сопоставить SHA-256 скачивания, File API и receipt.

Заверения модели, `done: true`, HTTP 200 и успешная валидация схемы по отдельности
не являются приёмкой. В частности, промежуточный `done` не заменяет финальную
выдачу, а пустой ответ без File ID не является готовым документом.

## Установленные расхождения

Lite прочитала официальный Word skill, но затем передала 99 команд при лимите
64 и команду `create` внутри batch, где она не поддерживается. Эти отказы
подтверждены receipts и журналом WebUI. После подсказки со штатным Markdown-
импортом успешно прочитала адресную справку и снова завершилась с пустым
текстом, без нового файла. Отсутствие Office-инструментов этим не объясняется.
Вывода «достаточно добавить инструкцию» эти данные также не подтверждают.

В окне сбоя gateway отвечал HTTP 200. Его обычный журнал не содержит исходного
`finish_reason` и тела ответа провайдера: точная причина пустого завершения
по этим записям не установлена. Общие параметры, reasoning, провайдеры и
промпты не изменялись по предположению.

Три отказа рендера `409` у Gemini 3.6 возникли при параллельных операторских
прогонах: у сервиса один слот снимка. Их нельзя приписывать неспособности
модели вызвать инструменты. Рендер впоследствии получен; оставшиеся прогоны
выполняются последовательно. Промежуточные ошибки и конечный результат
сохраняются раздельно.

## Проверка фактического контекста

Сопоставлены не только видимые сообщения, но и сохранённые native tool results,
а затем фактические запросы и потоковые ответы на штатных `request`/`stream`
границах OpenWebUI. Временный диагностический Filter был ограничен одним
синтетическим чатом, пользователем, моделью, сроком и объёмом записи. Он
возвращал исходные объекты без изменений и уже удалён; флаги остальных Functions
совпали со снимком до диагностики. Перезапуск и модификация core не требовались.

В последнем воспроизведении Lite получила три последовательных запроса.
В третьем было семь сообщений и 48 инструментов; полный текст заметки
сохранил 4824 символа и исходный SHA-256. Word guide также дошёл целиком:
42289 символов, SHA-256 UTF-8
`6088c33759270bdaa5853ccdc1de1be1efcb4aab6d2f268e6276f6bf2d0b1c9b`.
Ответ шлюза на этом шаге содержал ноль символов текста и ноль фрагментов
tool call, с `finish_reason: stop`. Это исключает потерю уже полученного
вызова инструмента внутри последующего цикла OpenWebUI в данном воспроизведении.

Отдельно фактический третий запрос пропущен через штатный `return_raw_request`
установленного LiteLLM 1.105.1. Это реконструкция преобразованного запроса
на текущем коде, а не запись исторического HTTP-трафика к Google. В полученном
Google body заметка и guide сохраняются полностью; `maxItems: 64` для команд
и `maximum: 2` для глубины остаются в схеме. Гипотеза об исчезновении этих
ограничений при конвертации данным опытом не подтверждается.
Обе присутствовавшие служебные подписи Gemini также сохранены: штатный LiteLLM
восстановил их из native tool-call IDs в Google `thoughtSignature`. Отсутствие
отдельного поля подписи в function JSON само по себе не доказывает её потерю.

При этом обнаружены реальные конфликты инструкций установленного guide:

- Пользователь требует сохранить поля `{{...}}` и пояснения, а общий delivery
  gate запрещает плейсхолдеры и требует удалить служебные пояснения шаблона.
- Guide предлагает `get --depth 3`, тогда как транспортный адаптер допускает
  только 0–2; Gemini 3.6 действительно получила соответствующий отказ.
- CLI-примеры включают `create/open/save`, тогда как создание файла и сохранение
  принадлежат адаптеру; команда `create` внутри его batch не поддерживается.
- Рекомендация дополнять малозаполненные страницы противоречит требованию
  перенести текст без новых сведений. Штатный Markdown-импорт в guide не описан.

Это доказанные расхождения контракта, но не доказательство конкретной причины
пустого ответа Lite. Один дополнительный системный промпт только в отдельном
тестовом чате не устранил сбой и не устанавливался как глобальное исправление.

В установленном LiteLLM нормальный `STOP` и несколько ошибочных причин,
включая `MALFORMED_FUNCTION_CALL`, преобразуются в одинаковый `stop`.
Поэтому пустой потоковый ответ нельзя считать доказательством нормального
завершения. Отдельный диагностический запрос через существующий шлюз без
потоковой передачи не дал ответа за 90 секунд; исходная причина им не
установлена. Временные файлы удалены, контейнер healthy, штатные проверки
и отдельный запрос доступности проходят. Повторный запрос не запускался.
Отключение streaming не предлагается как исправление: установленный native
OpenWebUI исполняет инструменты только в потоковом пути.

Первый кандидат с явным приоритетом сохранения источника проверен в отдельном
чате обычного пользователя. Lite создала и выдала скачиваемый DOCX: полный
текст совпал строго, все четыре таблицы совпали, UI-скачивание подтверждено.
SHA-256: `e6f632fd980745a6a3937a70ab3b81e35e6bec16212d14177602f1a8728f0b5c`.
Однако первый рендер и отдельный операторский повтор получили `502 Screenshot
is not a valid PNG`; визуальная приёмка этого файла не пройдена. Это другой
результат, чем прежнее пустое завершение, но ещё не полная приёмка Lite.
Короткий общий текст адаптера (1303 символа) тоже проверен в отдельном чате:
он снова завершился после чтения заметки без файла. Этот кандидат отклонён,
его исходник сохранён только в приватном evidence, в выпуск он не включается.
Прохождение 91 проверки Filter не было принято за подтверждение поведения LLM.

## Кандидат минимального исправления: готовая заметка как источник экспорта

Изолированный повтор на том же образе LiteLLM, с фактическим третьим запросом,
воспроизвёл пустой `stop`. После проверки узкого наблюдателя получена исходная
причина Google: `MALFORMED_FUNCTION_CALL`. В сообщении об ошибке модель пыталась
включить `command: create` внутрь `create_office_document.commands`. Это
подтверждение механизма на данном входе, а не запись исторического ответа Google.
Рабочий gateway не менялся; диагностический контейнер ограничен 512 МиБ,
0.5 CPU, 64 PID, без опубликованных портов, затем удалён.

Существующий `export_answer_to_word` уже импортирует подготовленный текст через
штатный Markdown batch, проверяет сохранение и изменение источника до публикации.
Сейчас его источники ограничены сообщениями assistant. Кандидат расширяет этот
же путь параметром `source_note_id`; нового экспортёра, хранилища и генератора нет.

| Значение | Владелец | Публичный контракт | Потребитель |
| --- | --- | --- | --- |
| Доступ и Markdown заметки | Native OpenWebUI Notes | `GET /api/v1/notes/{id}` с исходной сессией; `data.content.md` | Существующий HTTP-адаптер Office |
| Импорт и форматирование | Существующий `write_docx` и установленный OfficeCLI | Один штатный Markdown batch, затем необязательное форматирование | Тот же `export_answer_to_word` |
| Сохранение текста | Существующий `require_preserved_text` | Проверка реального DOCX и повторное чтение источника до upload | `write_docx` |
| Файл, права и вложение | Native Files/chat events | Прежние upload/attach и `result_file_id`/`download_url` | Обычный Web UI |

Метод чтения заметки — адаптер представления, не новый владелец Notes. `write_docx`
остаётся координатором прежнего порядка вызовов. Для заметки нужны проверенный
native ID, непустой Markdown и совпадение ID в ответе; нет fallback на JSON-редактор,
HTML, чужую заметку или переписанный моделью текст. Несовместимый выбор источников
отклоняется. Прежние previous/selected assistant и Action должны сохранить поведение.
Приёмка включает отказы 401/403, подмену ID, изменение реального источника и DOCX,
а затем полный пользовательский сценарий. До неё кандидат не считается исправлением.

Локально пройдены 176 проверок затронутого пути, включая прежние assistant/Action.
В полном Windows-наборе: 282 passed, 3 skipped, 7 failed в неизменённом
`test_terminal_file_transfer.py`/`terminal_file_transfer.py` при передаче
Windows `_TemporaryFileWrapper` в aiohttp multipart. Этот путь в кандидат не
включён. Штатный Linux CI с реальным закреплённым CLI обязателен; добавлена
проверка полного импорта заметки и отказа публикации при изменении реального
Markdown-источника между чтениями. Результат CI и пользовательская приёмка
кандидата ещё не получены.

Дополнительно сохранён обрезанный результат штатного screenshot renderer:
PNG 8192 байта, 1380×1920, `Truncated File Read`. Контроль с ограниченной задержкой
очистки не проверил гипотезу раннего завершения дочернего процесса: CLI в том
прогоне не смог запустить headless backend. В контейнере после проверки 4 PID
при лимите 256, zombie нет. Ни причина обрыва PNG, ни исправление renderer пока
не установлены; код завершения процессов и рендера не менялся.

## Исследование upstream и границы визуальной проверки

Изучены первичные источники разработчиков:

- [LiteLLM #19789](https://github.com/BerriAI/litellm/issues/19789):
  закрытый отчёт о пустом Gemini tool-calling stream с ошибкой
  `MALFORMED_FUNCTION_CALL`, превращённой в успешный `stop`. Механизм потери
  причины согласуется с установленным кодом; исходная причина именно нашего
  потокового ответа пока не получена.
- [OpenWebUI #27650](https://github.com/open-webui/open-webui/issues/27650):
  соседняя проблема выдачи файлов Open Terminal, закрыта с указанием реализации
  в dev. Она не объясняет исходное отсутствие OfficeCLI у DeepSeek и не
  подтверждает поведение установленной версии.
- [OpenWebUI #28492](https://github.com/open-webui/open-webui/issues/28492):
  пустые ответы и потеря tool calls/signatures на прямом Google OpenAI endpoint.
  Текущий маршрут использует существующий Google gateway, поэтому сходство
  симптома не доказывает тот же механизм.
- [Google SDK #2575](https://github.com/googleapis/python-genai/issues/2575):
  открытый отчёт о пустом `STOP` после инструмента в Gemini streaming AFC.
  Это наблюдение другого стека, не доказанная причина нашего случая.
- [OfficeCLI #483](https://github.com/iOfficeAI/OfficeCLI/issues/483):
  разработчик сообщил исправление одноколоночной сетки в `main` для будущего
  релиза. Установка исправления у нас не заявляется; используется `grid >= 2`.
- [OfficeCLI #485](https://github.com/iOfficeAI/OfficeCLI/issues/485):
  обрезание диапазона снимков; исправление PPTX в `main` и отдельный DOCX PR
  нельзя выдавать за установленный общий фикс.
- [Word guide 1.0.152](https://github.com/iOfficeAI/OfficeCLI/blob/v1.0.152/skills/officecli-docx/SKILL.md):
  версия закреплена по фактическому инструменту; точные команды уточняются
  установленной справкой.

На Linux OfficeCLI использует HTML-предпросмотр. Уже действующее описание
`render_office_file` предупреждает: одиночная первая страница пропускает
пагинацию и может создавать ложное переполнение. Проверять общий вид нужно
через `grid`, а не менять документ ради такого снимка.

Попытка независимого экспорта скачанных копий через локальный Microsoft Word
не завершилась. Ограниченная проверка остановлена; только созданные ею процесс
Word и COM-helper завершены после сверки PID, времени запуска и команды.
PDF не получен, проверка реального Word не заявляется. Приёмка рендера означает
читаемость штатного HTML-предпросмотра, а не гарантию идентичной печати в Word.
В некоторых таблицах остаются переносы длинных полей и заголовков; их текст
сохранён. Это шаблон с плейсхолдерами, не заполненное предложение заказчику.
