# OfficeCLI: аудит маршрута создания протокола

Дата: 06.11.2026. Объём: диагностика без изменения приложения, конфигурации,
профилей, данных чата и без новых запросов к LLM. Отчёт и диагностические
материалы созданы только локально. Проверены документация, исходники, живая
SQLite в режиме `mode=ro` / `query_only`, установленный код и сохранённые
tool call/result последнего задания.

## Вывод

Гипотеза «исправленный Filter не назначен gpt-6-luna» не подтвердилась:
модель есть в действующем `target_model_ids`, Function Active/Global,
установленный код совпадает с исходником. Однако задача действительно выполнена
обычной Luna напрямую, без фиксированного Terra-worker, чтения
`artifact-workflow` через native Skill tools и без native Tasks.

Здесь существуют два разных маршрута. Worker введён для отдельного профиля
«Корпоративные документы», а не для всех прямых моделей. Дополнительно доказан
разрыв между намерением Filter «автоматически загрузить workflow» и семантикой
установленной OpenWebUI: выбранный `skill_ids` при доступных native Skill tools
даёт описание в каталоге, а не обязательный текст инструкций. Чтения этого Skill
в исследуемой ветке нет. Это подтверждённый пробел гарантированной передачи
workflow; его вклад в каждую последующую правку нельзя установить по одной истории.

## Документированный путь и реальная конфигурация

| Область | Требование / намерение | Наблюдение | Оценка |
| --- | --- | --- | --- |
| Подключение Luna | Прямые модели получают OfficeCLI через один Filter | Luna в live allowlist; Filter Active/Global; 49 реальных OfficeCLI-вызовов | Подтверждено |
| Workflow | Filter добавляет `artifact-workflow` при Office input | Live Valve указывает правильный Skill; source/hash совпадают | Назначение настроено, фактическое чтение не подтверждено |
| Передача правил Skill | Методика должна управлять большой файловой задачей | В native UI выбранный, но не упомянутый Skill представлен manifest ID/name/description; текст требует `view_skill` | Подтверждён разрыв гарантии загрузки |
| План / Tasks | Skill требует native tasks для большой задачи | Нет `create_tasks`/`update_task`; `chat.tasks=null` | План в native Tasks не создан |
| Фиксированный worker | Corporate lead передаёт полный Skill, факты и оригинал одному Terra-worker | Этот чат использует прямую Luna; у неё нет binding `corporate_document_delegation` | Корпоративный маршрут здесь не выбран |
| Цепочка версий | Продолжать с последнего успешного `result_file_id` | Все пять успешных apply последовательно используют предыдущий результат | Подтверждено |
| Публикация | create/apply сохраняют копию и прикрепляют её | Один create и пять успешных apply дали шесть вложений | Соответствует нынешнему контракту адаптера |
| Остановка после приёмки | Не менять оформление без конкретного дефекта | Есть циклы переноса одного абзаца, его удаления и новой раскладки таблиц после проверок | Требует разбора рендеров; число версий само по себе не доказывает ненужность правок |

Обычный путь описан в [OfficeCLI runbook](../../infra-ops/officecli-openapi-docx-release.md),
условие и назначение — в
[Filter](../../../deploy/openwebui-functions/officecli_auto_attach_filter.py),
правила Tasks/прогресса/остановки — в
[artifact-workflow](../../../deploy/openwebui-skills/artifact-workflow.md).

Корпоративный путь описан в
[runbook библиотеки](../../infra-ops/corporate-template-library.md), раздел
«Три native-профиля и фиксированный worker», и
[native export профилей](../../../deploy/openwebui-tools/corporate_template_models.json).
Документация прямо ограничивает выпуск этим профилем и запрещает при его
установке менять прямые профили, глобальный OfficeCLI Filter и глобально включать
native subagents. Поэтому отсутствие worker в обычной Luna не является
доказательством поломки корпоративного пилота или потерянного назначения Filter.

Live `corporate-documents` имеет только custom Tool
`corporate_document_delegation`, base model `gpt-6.1-terra`.
В live Valves Tool: `DEFAULT_MODEL=corporate-office-worker`,
`AVAILABLE_TOOL_IDS=server:officecli`, `MAX_ITERATIONS=12`,
`MAX_PARALLEL_AGENTS=1`, `APPLY_INLET_FILTERS=true`.
Хеш Tool совпадает с закреплённым в runbook upstream-файлом:
`790de1a09eea5467ad7f87568f20c00099f7ca8c8ef1b946e55799d742c45fbe`.
Worker имеет только OfficeCLI. Native Tasks у корпоративного lead и worker
выключены явно; это отдельный механизм, а не следующий этап обычного TODO-пути.
Глобальные native subagents выключены; они не эквивалентны этому custom Tool.
Нового продуктового прогона корпоративного маршрута в аудите не было.

## Проверка границы контекста без LLM

Из установленного Filter выполнен локальный replay с фактическими live Valves,
ID модели и файловыми метаданными ветки. Проверены два входа:

1. Без top-level `body.files`: добавляется OfficeCLI; Skill/Terminal не добавляются.
2. С файлами ветки в `body.files`: добавляются OfficeCLI, transfer Tool,
   `artifact-workflow` и native function calling. Worker не выбирается.

Последний user message не имел собственных вложений, DOCX был в начале ветки.
Исходный top-level `body.files` запроса не сохранён, поэтому первый вариант
не объявляется установленной причиной. При включённых native Skills доступные
Skills всё равно обнаруживаются через общий каталог.

В runtime middleware проверены строки 2850–2953: `skill_ids` объединяется с
model binding, но выбранные Skills без явного упоминания при включённых
builtin Skill tools попадают в `available_skills` только как описание.
Исполнен точный AST-фрагмент этого установленного цикла для `artifact-workflow`:
получены ID/name/description; правила `native tasks` и остановки изменений в
полученном manifest отсутствуют. Это не эмуляция ответа провайдера.

Для Luna `capabilities.builtin_tools=true`, отдельного выключения
`builtinTools.tasks` или `builtinTools.skills` нет. Установленный
`utils/tools.py:852–867` допускает Skill tools и Tasks для сохранённого native
UI-чата. `chat.tool_search.enable=false`: отложенный поиск schemas не является
текущей причиной. Исторический полный tools array не записан; доказать по
сохранённому ответу точный состав всех доступных модели tools нельзя.

## Следующий минимальный шаг

Сначала обеспечить применение существующей методики в обычном Office-пути:
проверить штатный способ гарантированного чтения/передачи `artifact-workflow`
до первой записи и поведение большой задачи с native Tasks. Не дублировать
текст Skill в новом промпте и не вводить второй workflow. Приёмка должна
проверять фактический контекст модели, сохранённый план, причины повторных
правок, последний File ID и результат по источнику.

Распространение фиксированного worker на обычные модели — отдельное изменение
продуктового маршрута; текущая поставка этого не делала. Само переключение на
worker не гарантирует единственное вложение: публикация на каждом create/apply
остаётся в существующем адаптере и требует самостоятельного решения, если
пользователю должна быть видна только финальная версия.

Приватные диагностические данные, команды с содержимым протокола и точные
runtime-исходники сохранены вне Git в `local/office-routing-audit-20261106/`.
`routing-replay.safe.json` содержит результат ограниченного replay.
Рабочие сервисы, настройки, пользовательская сессия и evidence чата сохранены;
временные серверы/контейнеры/наблюдатели не создавались.
