# OfficeCLI: native workflow перед записью файла

Дата: 06.11.2026. Статус: реализация выпущена и принята. Git-поставка — PR #587.

## Результат и границы

Existing Filter активирует настроенный `artifact-workflow` через
`metadata.chat_context.mentioned_skill_ids`. Native Skills загружает полный root
с действующими ACL и version pin до вызова модели. Методика остаётся в одном Skill.
Маршрут охватывает обычный прямой OfficeCLI-чат, создание без вложения и продолжение
с файлом в истории. Прежние исключения для auxiliary tasks, явно заданных tools и
отдельных профилей сохранены. Terminal по-прежнему зависит от Office input.

Core, модель-worker, оркестрация и механизм публикации не менялись. Строго один
DOCX не является критерием: успешная правка штатно публикует следующую версию.
Недоступный/неактивный Skill либо root более native лимита 20 000 символов нельзя
считать полной загрузкой. Проверенный опубликованный root содержит 8002 символа.

В существующем Skill уточнены правила проверки полного источника, статусов решений,
содержательного Tasks-плана и сохранения формы при ремонте повреждённого DOCX.
Новая методика и отдельный владелец контекста не добавлены.

## Проверки границы контекста

96 focused tests пройдены. Предварительная до/после-проверка использовала фактическую
ветку из семи сообщений, точные установленные native Skill loop, formatter и
Responses converter. Snapshot IO задан отдельно проверенными данными native API;
полный runtime middleware локально не исполнялся. Проверены создание/продолжение,
сохранение других Skill IDs/pins, идемпотентность и исключённые маршруты.

В реальных provider-boundary payload обычной Luna полный root и полная timed-
расшифровка (146016 символов) присутствовали ровно по одному разу, вместе со схемами
`create_tasks`/`update_task`. Это подтверждено до первой записи и в 20 requests
основного второго прогона, включая resume после ask_user, затем в 8 requests QA.
Модель создавала native Tasks до apply. Независимое финальное ревью выявило
ограничение: Tasks содержали четыре общих этапа без перечня конкретных частей
источника. Уточнённый пункт 4 Skill модель не выполнила; полное соблюдение
методики не доказано. Для узкого GOAL подтверждены доставка контекста, создание
и завершение плана, работа с последним File ID и принятый после QA документ.
Чтение display summary не принималось за
полноту источника. Native delegation для прямой Luna не заявляется.

## Приёмка протокола

Исходный чат не менялся. Проверки проведены в native forks под той же обычной
учётной записью, той же Luna, с исходной формой, полной расшифровкой и естественным
заданием «Собери полный протокол по форме клиента “Ваниль” из этой расшифровки».

Первая попытка с прежним текстом Skill остановлена и не принята: методика/Tasks
были в контексте, но модель потеряла элементы формы и содержание. После уточнения
существующего Skill второй прогон сохранил правильную загрузку методики, но
исходный DOCX имел 300 schema errors. В native ask_user выбран предложенный вариант
ремонта копии; код/CLI оператором не подсказывались. Модель использовала existing
stage_chat_file, Terminal/LibreOffice и publish_terminal_file.

Четыре публикации второго прогона связаны с ремонтом пакета и проверками:
`3f2bf3e1` (256 ошибок), `03acbb34` (20), `798a2e50` (0), `53d892e1`
(завершённая первичная версия). Последняя не прошла независимую смысловую приёмку.
В том же обычном UI переданы пять содержательных замечаний с таймкодами:
неизвестные дата/место, согласованный маршрут обращений, закрытые периоды,
скрытые дефекты/дополнительный объём и отраслевой мониторинг. Выполнены две native
apply-правки последней копии. Всего во втором fork шесть DOCX-публикаций;
снижение количества версий не доказано и не заявляется.
