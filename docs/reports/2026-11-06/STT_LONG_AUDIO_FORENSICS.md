## Где исчезает исходная ошибка

1. [lemonfox.py](../../../services/stage2-stt/stage2_stt/lemonfox.py):95–109: timeout=120; любой HTTPX HTTPError превращается в provider_network_error. Тип исходного исключения остаётся только в цепочке Python __cause__, явного logging нет. Ошибочный HTTP-ответ провайдера нормализуется отдельно (:161–179), с provider_status_code и ограниченным кодом/сообщением.
2. [app.py](../../../services/stage2-stt/stage2_stt/app.py):218–224: оба случая превращаются в наш HTTP 502; JSON detail содержит job_id и нормализованную ошибку.
3. [Filter](../../../services/stage2-stt/openwebui_filters/stage2_audio_context_filter.py):558–560: для любого 5xx сразу возвращается общая фраза; JSON detail не разбирается. job_id и код ошибки не сохраняются в File или чат.
4. [job_store.py](../../../services/stage2-stt/stage2_stt/job_store.py):14–22: failed job хранится только в памяти процесса. Штатный GET jobs/{job_id} существует, list/search отсутствует. Процесс не перезапускался, поэтому запись может ещё существовать; её ID в исследованных источниках не найден. Attach/dump памяти не выполнялись.

Docker logs обоих контейнеров за 12:58–14:32 не содержат provider_network_error, provider_error, ReadTimeout, WriteTimeout, ConnectTimeout, Traceback или stt-<32 hex>. Обработанный HTTPException не обязан оставлять traceback. Privoxy logfile пуст, journal за окно без записей. Xray journal содержит accepted connections, но не исходный HTTP-код/ответ внутри TLS.

## Размер, ожидание и изменение транспорта

Текущая подготовка использует фиксированный MP3 64k/mono/16k. Runtime limits: max_direct_upload_mb=100, max_prepared_audio_mb=100, too_large=FAIL. Отдельного адаптивного сжатия при превышении 100 МБ в проверенном пути нет. Текущий файл ниже лимита. Официальный direct-upload лимит — 100 MB; локальный расчёт использует MiB (100×1024²). Разница единиц существует, но этот файл её не затрагивает.

HTTPX timeout=120 — лимиты отдельных сетевых операций, не общий wall-clock deadline. Разница примерно 125–127 с совместима с timeout, но не различает read/write/connect либо ответ сервера. Первый отказ без завершённого access log не объясняется этой корреляцией. Внешний Filter timeout по умолчанию 360 с; первый следующий OpenAI connect отмечен в 13:07:26, через шесть минут. Это временная корреляция, не доказательство типа исключения.

В [сегодняшней приёмке транспорта](TRANSPORT_XRAY_GOAL.md) зафиксирован переход на Xray. Существующий private receipt stt.safe.json: synthetic WAV 220,710 байт, 11:32:22 UTC, Stage2 200/completed, 7.529 с, result readback совпал. Это проверка короткого запроса, не большой передачи. Данный переход предшествует текущему инциденту; связь с регрессией длинных записей не доказана. Раньше успешные длинные файлы в этом расследовании независимо не извлекались. Hardcoded timeout=120 присутствует уже в Git commit 9cb675f3 от 19 июня.

## Замечания KISS / native

- Подтверждённый разрыв: штатная структурированная ошибка уже существует на нужной границе, но фильтр выбрасывает её вместе с job_id. Для выяснения причины нужен существующий owner, новый диагностический сервис не требуется.
- Второй разрыв: сетевое исключение нормализуется так, что пропадает его тип; native logs его не фиксируют. Один общий 502 затрудняет диагностику и вводит в заблуждение при чтении UI.
- Ручка называется jobs, но выполняет provider call синхронно; запись job недолговечна и недоступна для поиска без потерянного ID. Это ограничение текущего контракта, не доказательство необходимости новой очереди.
- Упор в память — отдельное измеренное наблюдение, не основание автоматически увеличивать лимит или объявлять memory leak.

## Согласованное включение диагностики, 17:49 МСК

После отдельного разрешения пользователя изменён только существующий Filter `_call_sidecar`: при HTTPX-ошибке пишет один `stage2_stt_failure` в штатный Python/server log. Поля: chat_id, message_id, file_id, error_type; при HTTP-ответе — sidecar_status_code и безопасная выборка существующего detail (job_id, code, retryable, provider_status_code, provider_error_code). Строковые значения detail ограничены 256 символами. Provider message, URL, токен, filename, email, envelope и аудио не логируются. По сохранённому job_id штатный GET позволяет прочитать нормализованную ошибку с provider message, пока живёт процесс STT.

Диагностика различает provider_error с HTTP-статусом Lemonfox, provider_network_error внутри STT и HTTPX-исключение внешнего Filter→STT. Подтип сетевого исключения внутри STT по-прежнему не сохранён; эта узкая правка не обещает восстановить его.

- Локально: 192 STT-теста passed, включая пять новых сценариев transport-boundary diagnostics/privacy/success. Независимый source review существенных замечаний не выявил. Модельные запросы и аудиотранскрибация при проверках не выполнялись.
- Обновление через штатный `POST /api/v1/functions/id/stage2_audio_context_filter/update`; exact source readback совпал, API обновляет native module cache. Core и контейнерные образы не изменены. Container ID/start/restart count сохранены, healthy; valves, active/global и имя функции сохранены.
- Deployment UTC: `2026-11-06T14:49:35.509164+00:00`.
- Filter после обновления: `c3ea5f13510936712be43564521778abb770bbaf0abbbc2f8f89fb95f55570ef`.
- Rollback: `/root/stt-diagnostic-20261106T144935Z`, каталог 0700, backup/candidate/receipt files 0600. Восстановление — прежний content из before.private.json через тот же native update; valves не менялись. Архив намеренно сохранён для отката.

### Зафиксированное завершение этой попытки

В `2026-11-06T14:56:52.328927279Z` штатный WebUI log записал:

```json
{"chat_id":"18f4e762-c2ce-4f5a-8768-ca9f8dd3ed10","message_id":"bdb9a9f9-1d1f-49df-a851-1bcccac2eeec","file_id":"c40903a1-a024-44ed-bd98-e655c83314a9","error_type":"ReadTimeout"}
```

Это HTTPX ReadTimeout **Filter→Stage2**, через ~361 с от timestamp сообщения. sidecar_status_code/job_id отсутствуют: HTTP-ответ от Stage2 не получен. Данный исход отличается от прежних завершённых POST 502; переносить его как доказанную причину на все прежние попытки нельзя.

В 14:56:57 тот же исходящий socket Stage2→Privoxy всё ещё ESTAB: bytes_acked=30,702,028, Send-Q=4,166,792, rwnd_limited около 100%. Загрузка полного 58.8-МБ файла через этот путь ещё не завершена. Поэтому конкретный текущий отказ — исчерпание внешнего ожидания ответа при продолжающейся медленной исходящей передаче, а не доказанный ответ Lemonfox с ошибкой. Точное место ограничения пропускной способности за локальным proxy/tunnel требует отдельного исследования.

После ошибки native chat readback: done=true, модель вернула общий отказ; status содержит «Не удалось обработать аудио. Повторите попытку позже». Ответ рекомендует перезагрузку/смену формата, но эта рекомендация модели не обоснована найденной транспортной причиной.

Дополнительный lifecycle gap KISS/native: после прекращения ожидания в WebUI исходящая сессия Stage2 ещё существует с очередью передачи. Штатная цепочка не подтвердила синхронную отмену вложенной работы; дальнейшая судьба задачи/возможное списание у провайдера неизвестны. Не следует создавать дубликат повторной отправкой до прояснения. Сессия пользователя не отменялась, процессы сервиса не останавливались.

Ограниченный диагностический watch завершился штатно после найденной записи; постоянный follower не оставлен. Агент не повторял provider calls и не менял настройки. Диагностическое изменение принято реальным путём: корреляция chat/message/file и точный тип внешней ошибки появились в существующем журнале без source content/provider message/credentials.
