## Главный вывод

Инструменты DOCX и PPTX уже существуют у того же OfficeCLI Tool Server.
Разрыв находится прежде всего в выборе штатного режима исполнения:
Filter подключает `server:officecli` всем 12 профилям, но автоматически выбирает
Native только при нескольких XLSX. Подключённый tool не гарантирует цикл
«прочитать исходник → применить правку → вернуть вложение».

OpenWebUI сейчас 0.9.6. Live Filter Active/Global, версия
`0.9.1-qualified-catalog`, LF SHA-256
`f60a19ffe34e2b54b7f65f7f2477360480b6ffb35caca1d75738482f7578081c`.
В native tools list один `server:officecli`. Оба модельных valve содержат
12 ID; reasoning exception — `gpt-5.6-luna,gpt-6-luna,gpt-6-sol`,
но это исключение применяется только внутри автоматического multi-XLSX пути.

## Наблюдаемая цепочка проблемного DOCX

Чат: https://gpt.alpha-soft.ru/c/3ae7c644-68a9-4857-8d3b-4476f3e14a7e.

1. DOCX по ID `5f732749-2889-4f4e-9071-ee986cc17beb` доступен: content API
   HTTP 200, MIME DOCX, 77 103 байта, ZIP signature `50 4b 03 04`.
2. Два ответа Gemini 3.5 Flash содержат legacy tool source
   `server:officecli/inspect_office_spreadsheet` с ошибкой HTTP 502:
   `no XLSX attachment exists in the native message ancestry`.
   Это неверный выбор формата инструмента, не доказательство потери DOCX.
3. Оба ответа имеют `done=true`, пустой текст и не содержат выходного файла
   или native function-call output. Флаг done здесь не является успехом.
4. Последующий ответ GPT 6 Luna просит повторно приложить файл и не создаёт
   результат. Тот же DOCX при этом доступен через Files API.

Просмотрены 32 видимых чата текущего аккаунта: в четырёх обнаружены DOCX
вложения, PPTX-вложения в этой выборке не обнаружены. Это не аудит всех
пользователей, архивов или всех исторических запросов на создание презентаций.
В чате `f7bbcb8d-3ec5-4ecf-b86b-34cca09a29ea` есть native inspect/apply
и DOCX-вложения от GPT 5.4 Mini и Claude Opus 5. Их файлы сейчас скачиваются
с HTTP 200 (74 316 и 77 103 байта). Содержимое и сохранность оформления
заново не квалифицировались. Следовательно, DOCX-механизм существует;
универсальный отказ OfficeCLI или потеря всех исходников не доказаны.

## Локальный replay и дополнительные разрывы

[routes.json](artifacts/officecli-docx-pptx-audit/routes.json) содержит replay
точного live Filter с live valves и модельными параметрами: 12 моделей ×
10 сценариев, без вызова провайдера. Для одиночного/нескольких DOCX, одиночного/
нескольких PPTX, DOCX+PPTX, DOCX+одного XLSX, одного XLSX и создания без входного
файла Native остаётся только у четырёх явно настроенных профилей. Два XLSX
включают Native у всех 12. PPTX с двумя XLSX тоже включает его у всех 12,
но именно из-за наличия Excel, а не отдельной квалификации PowerPoint.
Chat-specific overrides в этом replay не задавались; у проблемного чата params пусты.

Другие подтверждённые ограничения/непроверенные предположения:

- Общая инструкция одновременно говорит «once per requested file» и
  «successful create result is terminal», «exactly its one attachment».
  Для нескольких выходных файлов это конфликт текста инструкции;
  пользовательский сбой по такому запросу пока не воспроизведён.
- Разрешение ближайшего вложения у адаптера типизировано для всех трёх форматов.
  Несколько DOCX или несколько PPTX требуют explicit `file_id`; выбирать первый
  молча нельзя. Специальная инструкция о source IDs сейчас привязана к multi-XLSX.
- DOCX inspect уже отдаёт annotated content и `table_layout`; существующее
  исправление fixed-form путей/неканонического OOXML не нужно переписывать.
  DOCX create/apply ограничены 64 командами, PPTX create/apply — 256.
- PPTX inspect выполняет `query ... shape --json`. Наличие этой операции не
  доказывает полноту видимого контекста для заметок, masters, тем и любых сложных
  объектов. Сохранность незатронутых частей нужно проверять на итоговом файле.
- Отказы Chat Completions от tools с reasoning установлены на GPT 6 в Excel
  canaries. Автоматическое исключение сейчас не охватывает Word/PowerPoint;
  нельзя включать их Native вслепую или скрыто снижать явно выбранный effort.
- Backlog #473 о preview PPTX отделён от получения правильного бинарного файла.
  OOM старого 29-XLSX чата (#527) также не объявляется причиной этого DOCX-сбоя.

## Документация разработчиков

подтверждает чтение, создание и правку всех трёх форматов.
[PPTX skill](https://github.com/iOfficeAI/OfficeCLI/blob/main/skills/officecli-pptx/SKILL.md)

генератор документов или второй файловый контур.

[Текущая документация OpenWebUI](https://docs.openwebui.com/features/extensibility/plugin/tools/development/)
ориентирует новые tools на Native и явно различает поведение до 0.10.0.
У нас 0.9.6: утверждение новых docs «Native по умолчанию» к установленному
runtime автоматически не применяется. Обновление ядра этим аудитом не предлагается.

## Контекст для следующего изменения и приёмки

Сначала определить единый штатный выбор Native для офисной работы и границу
reasoning, сохранив явно выбранные параметры, task guard, ACL и существующих
владельцев Tool Server/Files. Не создавать Workspace-дубликаты provider-профилей
ради обхода пробела. Устранить конфликт числа выходных файлов в инструкции
и обеспечить объяснимый ответ при ошибке вместо пустого успешного сообщения.

Базовая приёмка: 12 профилей × создание/редактирование DOCX/PPTX = 48 ячеек.
Каждая ячейка требует обычного чата, result_file_id, штатного вложения,
metadata/content HTTP 200 и проверки скачанных байтов. Для правки проверять
точные целевые изменения и сохранность незатронутого текста, структуры,
таблиц, форматирования; в PPTX — также других слайдов, объектов и связей.
Дополнительно нужны продолжение без повторной загрузки, model switch/reload,
несколько исходников одного формата и смешанные входы/выходы. Роли проверки
соответствуют реальной видимости моделей; выдача новых grants не подразумевается.

Контекста достаточно для узкого исправления маршрута и проектирования тестов.
Свежего доказательства работоспособности всех 12 профилей с Word/PowerPoint
пока нет. В этом аудите нет изменений production, новых пользовательских
сообщений, перезапусков, CI или публикации PR.
