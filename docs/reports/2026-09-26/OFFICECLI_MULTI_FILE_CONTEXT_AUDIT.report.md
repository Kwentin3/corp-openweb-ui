## Вывод

Файлы и идентификаторы не потеряны в хранилище. Все шесть вложений доступны через штатный Files API; SHA-256 скачанных байтов совпадает с сохранённым file_hash. Наблюдаемый разрыв — отсутствие file_id во всех четырёх запросах inspect_office_spreadsheet. Установленный стандартный маршрут выбора инструментов формирует отдельный запрос из текста сообщений до RAG-обработки файлов и не переносит поля files в текст запроса. Это объясняет, почему автоматический выбор работает с одной книгой и останавливается при двух.

Исторические запросы провайдеру не получены. Текущий контейнер OpenWebUI запущен после инцидента; объяснение исторического поведения по текущему коду является реконструкцией, а не побайтной записью исторического запроса.

## Владельцы и порядок обработки в установленном runtime

1. OpenWebUI владеет Files API и историей сообщений. Вложения содержат id, url=id, имя, тип и метаданные; parentId связывает сообщения.
2. Глобальный Filter officecli_auto_attach_filter, версия 0.8.4-compact-context-experiment, активен. gpt-5.6-luna входит в target_model_ids. Filter добавляет server:officecli и общую инструкцию inspect/apply, но не перечисляет разрешённые вложения и их ID.
3. У чата params={} и у модели params={}. Сохранённые tool_result citations соответствуют стандартному обработчику инструментов. Исторический эффективный runtime params отдельно не записан.
4. В utils/middleware.py:1263-1288 get_tools_function_calling_payload берёт текст последнего пользовательского сообщения и до четырёх предшествующих сообщений. Системное сообщение этого отдельного запроса строится из схем инструментов; существующие system-инструкции могут попасть лишь в ограниченную текстовую историю. Поля files и metadata.files не сериализуются в эту историю.
5. utils/middleware.py:2846-2879 добавляет attached_files только для function_calling=native, затем выбирает native tools или стандартный chat_completion_tools_handler. В стандартной ветке вызов инструмента выполняется до chat_completion_files_handler (:2891).
6. Стандартный обработчик (:1310 и :1330-1458) получает выбор инструмента от модели, исполняет его и сохраняет результат как source с tool_result=true. Видимый 422 не запускает здесь автоматический цикл исправления параметров.
7. OfficeCLI app.py:637-675: если request.file_id отсутствует, вызывается resolve_nearest_xlsx_attachment. Затем должны следовать скачивание и officecli view. При неоднозначности выполнение останавливается до этих двух шагов.
8. openwebui_client.py:_resolve_nearest_attachment читает историю через штатный Chat API, идёт по parentId, на ближайшем сообщении с подходящими XLSX дедуплицирует ID. Один ID выбирается; два вызывают OpenWebUiAmbiguousAttachment. Старые загрузки не объединяются с ближайшей парой для принятия этого решения. Уже первая пара достаточна для отказа.
9. После обработки инструмента OpenWebUI извлекает файловый контекст. get_source_context (:931-954) формирует source-теги с номером цитаты, именем и, если доступен, resource-id. Номер source id не является file_id. Этот поздний контекст нельзя приравнивать к входу предыдущего запроса выбора инструмента.
10. Финальная модель получает ошибку инструмента и извлечённые источники. В наблюдаемом чате она даёт неверные объяснения и просит действия, не меняющие контракт вызова.

Реконструкция текстовой истории для каждого из четырёх пользовательских ходов не обнаружила ни одного из шести ID. Это проверка сохранённого текста по установленному алгоритму, без внешних LLM-вызовов; она не учитывает неизвестные исторические дополнительные преобразования.

## Контракт OfficeCLI

file_id в NativeXlsxReference опционален; описание советует опускать его вместо угадывания. XLSX inspect описан как чтение single nearest attachment. Ошибка требует явный ID, но не возвращает список кандидатов. В установленном перечне операций нет отдельного перечисления вложений и нет операции объединения нескольких книг. Create создаёт новую книгу; apply редактирует одну.

Следовательно, нужно различать два вопроса: доступ агента к исходным книгам и возможность сохранного объединения. В этом чате второй вопрос ещё не проверялся: нет успешного чтения книг через OfficeCLI, вызова объединения или итогового result_file_id.

## Контекст для будущего исправления

Сначала обеспечить доступность карты разрешённых файлов «сообщение → имя → file_id» именно на этапе выбора инструмента через существующий native extension seam. Сохранить отказ от произвольного выбора одной книги из двух. Уточнить описание file_id: автоматический выбор допустим только при одном кандидате; повторная загрузка или переименование не устраняют множественность. Не переключать все модели на native без отдельной квалификации.

Проверка кандидата должна показать два явных правильных file_id при чтении пары, правильный выбор ближайшей загрузки, работу продолжения без новых вложений и отсутствие смешения старых/новых копий. Затем отдельно проверить возможность месячной сборки на копиях реальных книг, включая формулы, стили, рисунки и состав листов. Точные правила группировки дневных листов в месячные вкладки нужно установить до реализации объединения.

В рамках этого аудита production и исходный код не менялись; создан только этот отчёт. Существующие изменения рабочей папки не затрагивались.
