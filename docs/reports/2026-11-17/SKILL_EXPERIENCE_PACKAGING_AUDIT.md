# Упаковка и повторное использование опыта: аудит установленного стека

Дата: 17.11.2026, Europe/Moscow. Статус: аудит и проектное решение завершены;
независимая проверка этапа PASS. Этот документ — единственная запись аудита.

## GOAL и границы

Определить минимальный штатный процесс превращения проверенного опыта в
сопровождаемые возможности: диалог упаковки, точный выбор skill, доступные код и
ресурсы, отдельная история данных и продолжение в новом чате.

Обязательный охват: выбор между сохранённым результатом/скриптом/skill; отбор
подтверждённых правил; вопросы о существенных пробелах; metadata/discovery;
исполнение и сохранность; владелец и актуальная версия; исправление и возврат;
личное/командное использование; повтор, прерывание и сценарии приёмки.

Разрешён только аудит. Skills, настройки, исходники и бизнес-данные production
не изменялись; новые чаты и модельные задания не создавались. Локально сохранены
этот отчёт и ограниченные свидетельства. Независимые подзадачи проверяли native
Skills и Terminal/состояние; итоговое решение и live-проверки выполнены ведущим.

## Вывод и одно рекомендуемое решение

Использовать существующие native Skills и Office Linux. Для согласованной
дисциплины достаточно одного короткого Workspace Skill упаковки опыта: он
отбирает проверенные решения, выясняет существенные пробелы, выбирает нужного
нативного владельца и выполняет его операции. Собственный creator Tool, новый
реестр, маршрутизатор, сервис памяти и интерфейс не нужны.

Встроенный `/skills:create` уже выполняет общую авторскую работу. Новый
корпоративный Skill, если переходить к внедрению, должен добавлять только наш
контракт готовности и хранения; не копировать встроенный стандарт, справочник
API и существующий `corporate-template-authoring`. Это одна инструкция поверх
существующих инструментов, а не второй авторский backend.

Внутри одного процесса назначать владельца по природе результата:

| Результат | Единственный основной владелец |
| --- | --- |
| Инструкция/методика без исполнения кода | Workspace Skill: native content/files/history/ACL |
| Повторяемая программа с шаблонами | Terminal Skill: `~/.agents/skills/<id>/SKILL.md`, код и ресурсы рядом |
| Изменяемые настройки пользователя, входы, история, результаты | Отдельная папка workflow в постоянном пользовательском home Terminal |
| Опубликованный корпоративный DOCX | Существующий Files/Knowledge/publication workflow |

У Terminal Skill права определяются подключением и пользовательской файловой
системой; native per-skill grants Workspace на этот каталог не переносятся.
Раздача исполняемого пакета коллегам требует отдельной установки и проверки
аудитории, без переноса личного состояния автора.

Не создавать одноимённые полные копии инструкции одновременно в Workspace и
Terminal. У Workspace виртуальные файлы; автоматической установки пакета на
Terminal нет. Кодовый workflow следует сразу оформлять у файлового владельца.
`/skills:create` сам по себе всегда направляет автора в Workspace, поэтому
нельзя обещать, что эта команда автоматически установит исполняемый пакет.

### Репрезентативная проверка между чатами

Через два существующих чата одного сотрудника выполнены только native GET
`files/cwd`, `files/list`, `files/read` и `/skills`. Обе сессии получили один home.
`daily_report.py` и `config.json` читаются в обоих чатах с одинаковыми SHA-256.
Это доказывает доступ к этим сохранённым файлам между чатами; не доказывает
автоматический выбор workflow моделью.

Существенное наблюдение: `history.json` есть в списке, но native `files/read`
возвращает 403 `Permission denied` в обоих чатах. Stat: владелец — тот же Linux
пользователь, mode `0600`; скрипт/настройки имеют `0664`. Содержимое истории через
привилегированный обход не читалось.

Установленный `UserFS` читает файлы от серверного процесса через group access,
тогда как `run_command` запускает код через `sudo -u` владельца. Поэтому 403
просмотрщика не означает утрату истории или невозможность чтения её самим
скриптом. Код ежедневки сохраняет историю через `mkstemp` и `os.replace` без
явного сохранения прав; это согласуется с наблюдаемым `0600`. Исполняющий прогон
не выполнялся, так что успешное продолжение ежедневки не объявлено проверенным.
Исправление прав/кода остаётся отдельным изменением после аудита.

## Контракт упаковки и пользовательский диалог

Это предлагаемое содержание одного авторского Skill, а не созданный пакет.

1. Пользователь просит сохранить опыт. Агент кратко называет задачу, результат
   и предполагаемый состав. Сначала проверяет, нет ли существующего skill для
   обновления и достаточно ли простого сохранения результата/скрипта.
2. Из переписки и фактических артефактов отделяет принятые решения, доказательства,
   отброшенные попытки и неизвестное. Успешный exit code/слова модели не заменяют
   сверку результата с источником. Системные секреты, полную историю и правила
   чужих владельцев в skill не копирует.
3. Известное собирает сам; техническое проверяет; о пользовательском решении
   спрашивает кратко и объясняет последствия. Существенная неоднозначность
   оставляет черновик; необязательный пробел записывается ограничением.
4. Назначает native владельца из таблицы выше, входы/выходы, фактические пути,
   зависимости и место изменяемых данных. Для кодового workflow использует
   directory из native Terminal Skill и подтверждённый home, без username хардкода.
5. Сам готовит конкретные name/description. Для Workspace сверяет отдельные
   native поля и содержимое `SKILL.md`; tags не считает гарантией маршрутизации.
   Проверку версии, дату/основание приёмки и ограничения записывает в компактную
   справку пакета, без нового обязательного manifest-формата.
6. Использует штатные create/update/history/CAS для Workspace. Для Terminal
   фиксирует проверенный полный выпуск кода и ресурсов; существующий Git — если
   он уже владелец, либо сохранённый проверенный архив. Изменяемую историю
   пользовательского workflow в распространяемый пакет не включает.
7. Личный skill сохраняет в пределах запроса пользователя. Командную публикацию
   выполняет только через существующие права и согласованную аудиторию. Выдача
   ссылки/ZIP в чате сама по себе не предоставляет доступ другим пользователям.
8. Проверяет сохранённое содержимое/metadata и фактический путь применения.
   Возвращает название, способ вызова, где ресурсы/данные, что проверено и что
   осталось. Различает «сохранён», «доступен», «проверен», не создавая отдельной
   системы статусов.

Пример диалога: «Оформлю подготовку ежедневки. Код и шаблоны будут доступны в
Office Linux, история останется в вашей рабочей папке. Правила и последний
результат уже согласованы. Осталось решить: при отсутствии свежего источника
останавливаем обработку или переносим прошлые данные с отметкой об их дате?»

Обычный запуск использует принятый выпуск. Просьба изменить правило или
подтверждённая ошибка открывает отдельную доработку: воспроизведение, адресное
изменение, проверка, новая версия и явная совместимость с прежней историей.
Возврат к прежнему коду не откатывает накопленные данные автоматически.

## Минимальные следующие шаги, без внедрения в этом аудите

1. Оформить один короткий авторский Workspace Skill с контрактом выше. Использовать
   имеющиеся native tools; не менять глобальный Office Filter и не вводить router.
2. Взять один уже проверенный кодовый workflow как пилот. Оформить его Terminal
   Skill рядом с кодом/шаблонами и отдельно указать рабочую папку состояния.
   Сохранить исходные файлы и прежний рабочий комплект.
3. Разрешить подтверждённые препятствия конкретного пилота: права после атомарного
   сохранения, точный полный выпуск, параметры/повтор/период, читаемость истории.
   Не распространять особенности ежедневки на все будущие skills.
4. Выполнить только приёмку ниже на разрешённом пользователе/данных. Для долгих
   запусков задать срок выполнения и адресную остановку до старта; первый пилот
   вести последовательно, без обещания продолжения живого процесса из другого чата.

Первый личный пилот не требует общей библиотеки исполняемых пакетов, нового
хранилища, универсального конструктора, систем автоматического обучения или
обязательного Git-репозитория на каждый маленький skill. Командное распространение
кодовых пакетов требует отдельной проверки установки и прав; native sharing
Workspace не устанавливает программу в home другого человека.
