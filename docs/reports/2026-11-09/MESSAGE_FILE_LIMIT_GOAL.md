# GOAL: десять новых файлов на сообщение

Статус: frontend и продуктовый путь приняты; выпуск runtime image в работе.
Действующий контракт уточнён пользователем 9 ноября 2026 года.

## Результат и границы

В каждом сообщении пользователь может прикрепить не более десяти новых файлов.
После отправки в следующем сообщении снова доступны десять вложений. Все ранее
добавленные источники сохраняются в штатном контексте; агент может обращаться
к ним без введённого этой задачей ограничения десяти источников.

Эта формулировка заменяет обсуждавшийся ранее предел активных загрузок/обработок
на пользователя. Счётчики серверных работ, новые очереди и контракты завершения
обработки в задачу не входят. Штатная очередь сообщений сохраняет границы
отдельных отправок. Настройки размера и обработки файлов не меняются.

Приоритет: максимально KISS и штатные механизмы OpenWebUI. Сохраняются native
File, контекст, обработчики загрузки, media и существующие ограничения модели.

## Текущая опора

- База: `origin/main`, `b45181917d743371295aecb00d002d5f0c583121`.
- Изолированная ветка: `agent/message-file-limit-10`.
- Рабочая копия: соседняя `corp-openweb-ui-message-limit`; чужие изменения
  основной копии и остальные worktrees не затрагиваются.
- Production: OpenWebUI 0.12.2; текущий `rag.file.max_count = 10`.
- `MessageInput.svelte` уже считает текущие вложения и новые выбранные файлы.
- `Chat.svelte` ошибочно прибавляет `chatFiles` при проверке отправки.
- Подготовка: проверить возможность штатной настройки; при её отсутствии
  минимально адаптировать точную сигнатуру frontend в существующей сборке.

## Обязательная приёмка

- 11 новых вложений одного сообщения не принимаются; 10 принимаются.
- Добавление файлов частями в одно сообщение не обходит предел десяти.
- Последовательные сообщения 10 + 1 и 10 + 10 работают.
- Продолжение чата с более чем десятью источниками работает; доступ к прежним
  источникам сохраняется без усечения по этому лимиту.
- Поведение проверено через портал до и после исправления. Модели и внешние
  сервисы вызываются только в объёме, необходимом для ограниченной проверки.
- Исправление привязано к точному upstream, проверено в собранном frontend;
  необходимые CI и независимая проверка выполнены на согласованном кандидате.
- Свои тестовые чаты/файлы и временные процессы убраны после проверки.

## Полномочия и выпуск

Разрешены реализация, ограниченная проверка и подготовка проверяемого выпуска.
Не проводить тяжёлую сборку на production. Перезапуск и переключение production
выполняются только при отдельно установленном разрешении. Перед таким шагом
подготовить конкретный проверенный кандидат и откат.

## Проверенное состояние и следующий шаг

Создана чистая рабочая копия от актуального `origin/main`. MCP Playwright
`navigate -> snapshot` работает, портал открыт в существующей сессии.
Независимый review подтвердил отсутствие настройки для отдельного ограничения
сообщения: нужна адаптация проверки отправки. Также найдено штатное объединение
queued messages, способное собрать два набора по десять в одно сообщение.
Выбрана последовательная отправка существующих записей очереди с сохранением
их prompt/files и повторным drain после снятия native lock.

На production воспроизведено обычным пользователем: 11 файлов сразу и 10 + 1
в том же черновике отклоняются до upload; 10 файлов успешно отправлены, следующий
один файл загружен/обработан, но Send блокируется без нового model request.
Создан один синтетический чат; один основной модельный вызов выполнен, ответ
`ACK10`. Тестовые источники содержат только синтетические маркеры.

## Выпуск и обязательные оставшиеся шаги

Копирование текущего OCI image обычным `docker save` вернуло manifest без
необходимых blobs; native push также сообщил отсутствующий blob. Перенос
через временный loopback registry не исправил отсутствие содержимого у
источника. Домашний native pull закреплённой базы не завершился в пределах
согласованных ограничений. Собственная работа остановлена; домашние контейнер,
network, timer, каталог и два SSH-туннеля удалены, исходные 14 контейнеров
не изменились. Глобальная очистка Docker cache не выполнялась.

Проверка создания незапускаемого контейнера из production image прошла,
контейнер пробы удалён. Ограниченная упаковка готовых frontend-ассетов в тонкий
слой остановилась по deadline 240 секунд на native Docker ARG stage. WebUI
не перезапускался; очистка остановленного промежуточного объекта Docker ещё
требует подтверждения. Новые сборки на production не запускаются.

Для выпуска существующий CI workflow дополнен сборкой штатного runtime recipe
на GitHub runner, проверкой полного frontend и точного совпадения 288 backend
Python-файлов с работающим runtime. Их SHA-256:
`6f6e1b508b6065155c8a1b2add3d7c3aa8501cd8a7b866361be0583084f49283`.
Native image archive проверяется по legacy и транзитивным OCI refs, размерам,
digest и inspected image identity до публикации. Проверки отвергают реальные
классы ошибок: отсутствующий blob, повреждение и чужой image ID.

Остаются: завершить CI image build/export, проверить и импортировать готовый
image без сборки на production, подтвердить очистку Docker intermediate,
подготовить точный откат и получить разрешение на переключение WebUI.
После разрешённого переключения обязательна обычная пользовательская проверка.
GOAL целиком не завершён. Следующий шаг — CI готового runtime image.
