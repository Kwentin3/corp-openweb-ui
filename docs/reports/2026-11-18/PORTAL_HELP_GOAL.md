# GOAL: помощь по порталу и работе с ИИ в обычном чате

Дата: 18.11.2026. Реализовано, продуктовая приёмка и QA cleanup завершены.
Поставка исходников и её CI ведутся в [PR #598](https://github.com/Kwentin3/corp-openweb-ui/pull/598).
Единственная запись задачи; актуальные head/CI/merge принадлежат native PR.

## Согласованный результат

Сотрудник получает в обычном рабочем чате понятную помощь по действующим
возможностям корпоративного Open WebUI и эффективной работе с ИИ. Помощник
читает проверенные источники, уточняет существенные пробелы и честно сообщает
об отсутствии сведений. Отдельный помощник и изменение ядра не требуются.

Поставка: curated материалы из Git и первичных образовательных источников,
native Knowledge и короткая инструкция помощи, воспроизводимое обновление,
приёмка обычным сотрудником, scoped rollback и уборка собственных QA ресурсов.

## Решения и границы

- База: `ed5579520b95bc7ad0d8d853be9dc82025b24791`, отдельная ветка
  `feat/portal-help`, рабочая копия `corp-openweb-ui-portal-help`.
  Три независимых dirty файла корпоративных шаблонов в исходной копии сохранены.
- Документы о кандидате не становятся подтверждением внедрённого поведения.
  Текущая справка должна учитывать проверенную версию, роли и квалификацию моделей.
- Git владеет принятыми текстами; native Knowledge — хранением, индексом и ACL;
  Skills — правилами помощи; штатный chat/tool путь — вызовом модели.
  Синхронизация переводит представление, не придумывает содержание и разрешения.
- До выбора синхронизации сверить точные API установленной 0.12.2 и готовый
  официальный oikb; новый сервис/провайдер/ядро не создавать.
- Сначала локальная проверка запроса и корпуса, затем ограниченная платная серия.
  Первоначально до 12 ответов; после двух непрочитавших источник baseline,
  проверки исправленного discovery и адресного уточнения обещаний coaching —
  до 16 ответов при прежнем общем QA budget 0.80 USD. Не более 120 секунд одного ответа;
  при превышении native Stop и проверка task/chat состояния до повтора.
  Корпус и схемы проверяются до вызова модели. Продолжение сверх этих пределов
  требует записи причины и нового ограниченного бюджета в этой записи.
- Provider capture только для собственных saved QA chat IDs: TTL до 900 секунд,
  до 20 запросов, вспомогательные задачи исключены. Captures/сессии вне Git.
- Локальная работа через общий Windows executor (owner/TTL, общий policy).
  Удалённые команды имеют timeout; новые сервисы/сборки production не запускаются.

## Приёмка

1. Установленный корпус и Skill соответствуют принятым исходникам; сотрудник
   читает их без прав изменения, anonymous/private cross-user доступ запрещён.
2. Портальная помощь и советы по работе с ИИ появляются в обычном чате;
   фактические tools/results и окончательный provider context содержат нужные
   сведения и ограничения, без существенного усечения.
3. Ответы выполнимы, учитывают доступ, не обещают кандидаты/неизвестные функции;
   посторонняя задача не запускает ненужное обучение или запись данных.
4. Изменение/удаление источника воспроизводимо отражается в базе; повторная
   синхронизация не создаёт дубликаты. Пустой/невалидный источник обработан явно.
5. Проверен обычный chat и затронутые варианты с attached Knowledge, когда они
   есть в рабочем контуре. Проверка не ограничивается административным API.
6. Поставка изолирована; required CI после содержательной проверки; версии,
   ограничения, rollback и retained evidence записаны; QA ресурсы убраны.

  Attached Knowledge ограничивает query_knowledge_files и может игнорировать
  произвольный help KB ID. Выбор способа подключения требует runtime проверки.
- Независимо подготовлены шесть тем и 12 сценариев приёмки. Их факты сверяются
  с runtime; предложенная схема не является уже принятой реализацией.
- Созданы native Knowledge `4ac92c03-4254-4666-98e1-6fb3557e0391` и Skill
  `portal-help`, version `73a75940-9c0b-4b6e-83e2-e47f10843768`.
  Шесть документов completed, оригинальные байты/членство проверены; индекс
  содержит только указатели на файлы KB. Shared READ user:*, без shared WRITE.
- По live Skills от 16.11 подтверждено описание личных черновиков сотрудников;
  корпус уточнён по этому source. Квалификация всех моделей всё ещё не принята.

- Две содержательные coaching проверки дали полезный ответ, но не прочитали
