# Установка бюджетов сотрудников и откат

Статус 11.11.2026: стендовая поставка принята; пользователь разрешил production
в активном GOAL584. Эта инструкция не подменяет проверку целевого окружения.
Текущее состояние и незакрытые пункты — в [единственной записи GOAL584](employee-budgets-goal584.md).
Исторический стендовый actual42825996133 проверял строгую Usage-блокировку на
LiteLLM1.105.1/OpenAI SDK2.33.0. Этот контракт заменён решением пользователя:
текущий release использует штатный учёт и не включает специальные Usage guards.
Установка, DB/Redis/права и каталог на целевом сервере остаются отдельной приёмкой.
Рабочие маршруты ещё не переключены. Текущее состояние — в канонической записи GOAL.

## Что устанавливается

Существующий LiteLLM получает native budget DB/Redis, auth и callbacks;
существующий WebUI — backend-модули и native Functions/Tool. Нового сервера
учёта или отдельного хранилища денег нет. PostgreSQL, users, virtual keys и
SpendLogs остаются штатными владельцами финансового состояния LiteLLM.

Отдельный [Compose overlay](../../compose/openwebui.employee-budgets.compose.yml)
добавляется к существующим release Compose только при установке бюджетов.
Он использует сервисы `google-gateway-0122` и `openwebui-0122`; базовые файлы,
data volumes, сети и обычный release-путь не заменяются.

## Баланс провайдера и лимиты сотрудников

Уточнение от 11.11.2026: лимит сотрудника — разрешение на расход, а баланс
провайдера — реальные доступные средства на внешнем счёте. Назначение лимита
не резервирует деньги у провайдера. Один внешний счёт может обслуживать несколько
моделей и проектов; его баланс учитывается один раз для этого счёта.

Не все провайдеры и типы аккаунтов предоставляют поддерживаемый API чтения
денежного остатка. Доступность и права такого API нужно проверять для конкретного
подключения. Native `/provider/budgets` LiteLLM показывает внутренние бюджеты и
наблюдаемый прокси расход, а не подтверждённый баланс личного кабинета провайдера.
Универсальное получение внешних балансов остаётся отдельным
[открытым предложением LiteLLM](https://github.com/BerriAI/litellm/issues/34734).

Порядок эксплуатации:

- При наличии поддерживаемого API получать остаток с сервера и показывать сумму,
  валюту, счёт и время успешного чтения. Даже такой результат является снимком
  на указанное время, а не гарантией выполнения следующего запроса.
- Если API нет, администратор вручную сверяет остаток в личном кабинете.
  После пополнения или обнаруженного исчерпания средств сведения нужно сверить
  заново; частота плановой проверки зависит от скорости расхода.
- При ручном переносе суммы в операционные сведения обязательно сохранять
  пометку «из ЛК вручную», валюту и время проверки. Между проверками это
  «последний известный баланс», а не автоматически актуальный остаток.
- Если достоверной суммы нет, показывать «Баланс недоступен — проверить в ЛК»
  и ссылку на кабинет. Ошибка чтения или устаревшие сведения не означают нулевой
  баланс. Ручной снимок не меняет native spend, лимиты или историю расходов.

Не выдавать «внесено минус расход LiteLLM» за фактический внешний баланс:
пополнения, бонусы, расходы через другие подключения и задержка обновления цен
могут дать расхождение. Если такой расчёт когда-либо понадобится, обозначать его
отдельно как оценку. Для постоплатного аккаунта отсутствие предоплаченного
остатка само по себе не означает отсутствие доступа к API.

Пример: у сотрудника осталось 20 USD лимита, но общий предоплаченный счёт
провайдера исчерпан другими запросами. Провайдер может отказать в новом запросе;
личный лимит сотрудника сохраняется. Сообщать об исчерпании денег можно только
по подтверждённой причине отказа; таймаут или общий HTTP 429 её не доказывает.
Обновление месячного лимита сотрудника внешний счёт не пополняет.

**Граница реализации текущего этапа:** подготовлены информационная шапка,
раскрываемая статистика и ручной снимок через прежний Tool/два native подтверждения.
Снимки хранятся в защищённых Functions Valves существующего Filter, отдельно от
native cap/spend. Автор и время записи назначаются сервером; источник и время
проверки ЛК видны явно. Есть проверка текущей роли, точного сообщения и revision
снимка; native Valves не предоставляет CAS между параллельными администраторами.
Новый журнал денег не создаётся. Этот source принят в native run43018788862;
проверка установки и работы на production остаётся отдельным обязательным шагом.

Универсального native API внешних денежных остатков в выбранном стеке нет;
автоматический balance adapter конкретного провайдера пока не квалифицирован.
До такой квалификации сумма берётся из ручной проверки ЛК. Отсутствие API баланса
не препятствует native учёту и лимитам.

Состояние оплаты читается из существующих SpendLogs по событиям последних семи
дней, максимум двух страниц/200 строк и пяти секунд на открытие карточки.
Неполное/недоступное наблюдение остаётся неизвестным. Финансовый отказ признаётся
по native provider error_code 402 («требуется оплата») либо по сохранённому
известному структурированному финансовому коду провайдера. Общий HTTP 429,
native budget 422 и свободный текст этого не доказывают. Native SDK может терять
подробный provider code; для таких ошибок без 402 результат остаётся неизвестным.
В шапку не передаются тело ошибки, ключи и трассировка.
Успех снимает отметку только при подтверждённом реальном оплаченном запросе
после отказа: cache miss, отсутствие fallback, тот же оплачивающий scope.
Эта отметка не блокирует вызовы, не требует платных проб и не означает баланс 0.
Карточка остаётся снимком на время открытия. Новые события учитываются при
«Обновить данные» или повторном открытии; уже показанная HTML-карточка другого
чата автоматически не переписывается. Отдельного фонового опроса и push-канала нет.

Для общего счёта нескольких моделей в protected native `model_info` задаются
одинаковые `owui_billing_account_id` и читаемый `owui_billing_account_label`.
Без этой привязки сведения показываются отдельно по deployment, семейство моделей
или имя провайдера не доказывают общий счёт. Для подтверждения восстановления
`owui_billing_immutable_deployment_id: true` означает обязанность менять native
deployment ID при изменении учётных данных/маршрута. Предпочтительна штатная
генерация ID LiteLLM; при ручном ID это правило соблюдает оператор.
Без такой гарантии последующий успех не снимает подтверждённый отказ.

## Автоматические модели и публичные цены

Tool читает native каталог моделей WebUI, проверяет соединение с общим LiteLLM и
ACL сотрудника. Прежний `managed_model_ids` оставлен только для совместимости
с сохранёнными Valves и больше не определяет каталог. Новая разрешённая модель
видна с долей 0 и пометкой «новая», без записи в финансовое состояние при чтении.
Подтверждённое применение создаёт отсутствующее native назначение с hard cap 0,
затем применяет явно выбранное распределение. Прежние расходы/ключи/периоды
сохраняются; отозванные назначения не удаляются и их доли не перераспределяются
молча. Полностью отсутствующие бюджеты по-прежнему создаются отдельным явным шагом.

Существующий Filter активируется штатно как global и сам ограничивает действие
соединением общего LiteLLM. Native WebUI дедуплицирует global и model-scoped IDs;
новые модели получают тот же подписывающий request hook без ручного прикрепления.
Другие соединения, Pipes и штатные вспомогательные задачи не получают этот учёт.
Это область существующего расширения, без изменения core Open WebUI.

Индивидуальных тарифов нет. Managed preparation запрещает денежные overrides в
`model_info` и `litellm_params`; суммы берёт штатный public model cost map LiteLLM.
После запуска проверить применяемые ставки через `/model/info` и источник/время
через `/model/cost_map/source`. Неизвестная цена не заменяется нулём;
`block_requests_for_models_without_pricing: true` остаётся обязательным.
Публичный каталог LiteLLM может отставать от тарифов самого провайдера.

Для обновления без перезапуска оператор один раз включает native расписание
`POST /schedule/model_cost_map_reload?hours=6`, проверяет
`GET /schedule/model_cost_map_reload/status`; разовое обновление —
`POST /reload/model_cost_map`. Использовать штатный публичный источник, без
`LITELLM_LOCAL_MODEL_COST_MAP=True`, offline-режима или собственного monetary map.
В шапке показываются применяемые цены учёта, а время загрузки каталога не выдаётся
за дату начала тарифа. Отметка изменения сравнивает текущие ставки с сохранёнными
ставками запроса до последней загрузки каталога, если такое свидетельство найдено.
Старые native расходы не пересчитываются; лимиты и пропорции сохраняются.

## Подготовка до включения

1. Сохранить текущие image IDs, protected config/env, native connection settings,
   источники Functions/Tools/Models, Valves и ACL. Сделать штатную согласованную
   резервную копию WebUI DB и бюджетной DB. Секреты остаются в protected файлах,
   отдельно от Git и публичных отчётов.
2. Подготовить существующие native PostgreSQL/Redis и проверить доступ из
   контейнера LiteLLM. Read-only preflight11.11 подтвердил отсутствие этих
   зависимостей у действующего gateway. Для установки подготовлен отдельный
   [native persistence overlay](../../compose/openwebui.employee-budgets.persistence.compose.yml):
   постоянные volumes, закрытая сеть, PG16/Redis7 с закреплёнными digest,
   ограниченные ресурсы и healthchecks; наружу порты не публикуются.
   Не использовать disposable volumes, аккаунты или цены из proof-стенда.
3. Выбрать точный проверенный image ID/digest LiteLLM и WebUI0.12.2.
   Stock1.105.1 сам по себе не подтверждает наличие проверенной calendar-floor
   поправки. Сохранить её manifest и точную идентичность выбранного артефакта.
4. До включения custom auth создать и прочитать обратно native control-plane
   identities через stock management API. Master, shared gateway bearer, native
   management key и viewer key различны. Management — `proxy_admin` с явно
   разрешёнными маршрутами из существующего [bootstrap owner](../../scripts/goal584-budget-proof/prove_gateway_auth.py);
   сам proof-скрипт на production не устанавливается и не запускается.
   Viewer — `proxy_admin_viewer`, только `/spend/logs/session/ui`.
   Проверить роли и `allowed_routes` через `/user/info` и `/key/info`.
5. Согласовать конкретный каталог deployment IDs, маршрутов и реальных native
   цен. Wildcard gateway-конфигурация без проверки цен не является бюджетной
   конфигурацией. Проверить публичный pricing lookup после запуска;
   денежные overrides и индивидуальные тарифы не допускаются.

Protected budget env содержит `DATABASE_URL`, native Redis connection values,
`LITELLM_MASTER_KEY`, отдельный `OWUI_BUDGET_GATEWAY_SECRET` и native
`OWUI_BUDGET_OPERATOR_KEY` для управления бюджетами. Проверка формата
не заменяет проверку настоящих прав ключа. По решению пользователя 11.11.2026
специальные Usage guards не регистрируются: расчёт и применение лимитов штатные.

В protected LiteLLM config сохранить согласованный `model_list` и параметры
провайдеров. Добавить штатные настройки, заполнив Redis из реального подключения:

```yaml
general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL
  custom_auth: litellm_auth.gateway_auth
  custom_auth_run_common_checks: true
  missing_session_id: omit
  coordination_redis:
    host: os.environ/REDIS_HOST
    port: 6379
    password: os.environ/REDIS_PASSWORD
  fail_closed_budget_enforcement: true
  disable_spend_logs: false
  store_prompts_in_spend_logs: false
  proxy_batch_write_at: 1
litellm_settings:
  callbacks: [budget_errors.handler, pricing_snapshot.handler]
  block_requests_for_models_without_pricing: true
```

Это фрагмент, не самостоятельный runnable config: model/protocol profiles
должны быть квалифицированы отдельно. Не переносить отсюда Redis password/port,
если реальное подключение использует иной native вариант.

Текущий release использует `positive-floor-v1.105.1`: pinned штатный LiteLLM
с ранее проверенным исправлением месячного сброса в двух функциях.
Образ собирается вне production существующим
`scripts/goal584-budget-proof/build_native_floor_image.py --variant positive-floor-v1.105.1`
с отдельными абсолютными `--context` и `--receipt`; builder проверяет base digest,
исходные/итоговые hashes и сохраняет immutable IID. Image-only workflow закрепляет
точный commit запуска. Прежний стендовый `stream-usage-v1.105.1` с raw-usage и
deferred-guard cancellation delta больше не входит в выбранный production release.
`unknown_usage_guard.py` и `budget_runtime.py` не монтируются и не регистрируются.
При неполной Usage штатный расход может отличаться от внешнего счёта: лимит
ограничивает учтённое LiteLLM значение. Отсутствие данных не выдаётся за бесплатный
запрос и само по себе не блокирует модель сотруднику.

## Подключение и проверка

Для подготовки единого маршрута используется существующий
`deploy/openwebui-upgrade-0122/prepare_google_gateway.py` с обоими параметрами:

```text
--root /opt/openwebui-upgrade-0122/<phase>
--managed-config /opt/openwebui-upgrade-0122/<phase>/private/approved-litellm.json
--managed-env /opt/openwebui-upgrade-0122/<phase>/private/approved-litellm.env
```

Это подготовка новой защищённой фазы, без применения native config или запуска
контейнеров; существующий gateway она не перезаписывает. Входной JSON является
штатным конфигом LiteLLM в YAML-совместимом формате и копируется точно, без
построения второго каталога тарифов. Оператор задаёт подключения; публичные цены
приходят через штатный каталог LiteLLM.
Env содержит разные master/operator/shared inference keys и native DATABASE_URL.
Обязательны только callbacks `budget_errors.handler` и `pricing_snapshot.handler`;
профиль с прежними `budget_runtime.*` отклоняется, чтобы не вернуть строгую блокировку.
Для managed Responses alias требуется уже квалифицированный native профиль:
`model_info.mode=responses`, `supports_native_streaming=false` и
`litellm_params.model=openai/<wire model>` без другого custom provider override.
LiteLLM получает полный upstream HTTP response; WebUI сохраняет SSE/Tools.
Подготовка пока сохраняет этот ранее квалифицированный транспортный профиль;
он больше не служит доказательством полноты Usage.

Managed-подготовка читает native `/openai/models`, сохраняет API type Responses/CC,
prefix и разрешённые metadata headers, направляет все enabled connection slots
в тот же LiteLLM и помещает в WebUI только shared inference bearer. Disabled
connection slots очищаются от URL, ключей и скрытых credential headers; исходная
конфигурация сохраняется в protected source snapshot. Неоднозначные активные
подключения, конфликтующие headers, отсутствующие aliases/цены и fallback вызывают
отказ подготовки. Ошибка managed-профиля не переключает её на legacy-режим.
Default CC bootstrap остаётся исторической транспортной подготовкой; для включения
бюджетов применяется только managed-режим и бюджетный overlay.

Перед включением подтвердить `direct.enable=false`, `ollama.enable=false`,
native attachment/активность бюджетных Functions и service task binding.
Низкоуровневый native model helper сам request Filters не запускает. OCR внешнего
загрузчика подписывает отдельную служебную операцию `document_ocr` с настоящими
actor/File IDs через общие модули; chat/answer root для неё не создаётся. Плательщик —
служебный бюджет платформы из common `service_payer_id`, не сотрудник. Нужны native
назначение этого плательщика на OCR model alias и его лимит. Отсутствие конфигурации,
неподходящий gateway/model или неподписанный вызов останавливают запрос до провайдера;
прямого fallback нет. Расход OCR учитывается штатно, без специальной блокировки
по неподтверждённой Usage. Raw Responses и native File ACL
сохраняются; новая обвязка не меняет содержимое PDF и инструкцию распознавания.
Неактивные broker direct adapters требуют отдельного включения в общий путь
перед активацией; наличие их файлов не означает работающий обход.

В существующем protected Compose env задать `EMPLOYEE_BUDGET_LITELLM_IMAGE`,
`EMPLOYEE_BUDGET_CONFIG_FILE`, `EMPLOYEE_BUDGET_ENV_FILE` и
`EMPLOYEE_BUDGET_MODULES_DIR`. Последний — каталог исходников
`deploy/openwebui-budgets` выбранной поставки. Overlay монтирует отдельные файлы
под точными runtime names; каталог целиком и стендовые модули не монтируются.
Проверить итоговый Compose командой `docker compose ... config --quiet`, затем
перечень mounts/image IDs. Обычный вывод `config` может раскрыть protected env.
Проверка Compose не доказывает import/runtime или продуктовую приёмку.

После отдельного разрешения установки подключить модули и установить через
native Workspace/API ресурсы из выбранной поставки:

|---|---|

| Details Action | `employee_budget_cost_details` / [cost_action.py](../../deploy/openwebui-budgets/cost_action.py) |
| Admin Tool | admin-only Tool / [admin_tools.py](../../deploy/openwebui-budgets/admin_tools.py) |
| Monthly budget Event | `employee_budget_monthly_view` / [monthly_view.py](../../deploy/openwebui-budgets/monthly_view.py) |

| OCR Event | существующий OCR Function / [luna_pdf_ocr.py](../../deploy/openwebui-functions/luna_pdf_ocr.py), с общими budget modules |

Проверить source/ACL readback, включить Filter/Action и, если используется,
service Pipe; прочитать `is_active` обратно. Filter/Action прикрепить к согласованным
Models и проверить сохранённые `filterIds`/`actionIds`.
В admin-only Valves `employee_budget_cost` задать `ledger_base_url` (корень LiteLLM
без `/v1`), `ledger_read_key` (viewer), `ledger_admin_key` (management).
Tool Valves `managed_model_ids` содержат выбранные native Model IDs без ключей.
Для согласованных service tasks явно задать common `service_payer_id`, Pipe Valves
`target_model_id` и native `TASK_MODEL`/`TASK_MODEL_EXTERNAL=employee_budget_service`;
проверить разрешения на исходную и целевую модель. Месячный шаблон задавать явно,
не сбрасывая существующие назначения. Лимиты сотрудников задаются готовой формой
с native подтверждением.

Администратор открывает управление из чата («Давай поработаем с лимитами»).
Рабочая карточка — плотная таблица с закреплённой шапкой: поиск/отдел, сортировка
по учтённым суммам, фильтр остатка и легенда моделей. В строке одна полоса100%
лимита; N−1 нативная граница меняет две соседние доли. Полоса даёт шаг1%, точные
десятичные доли доступны в «Доли». Невалидные доли не нормализуются автоматически.
Фильтры/сортировки не вызывают модель и не теряют черновик; применение включает
все отдельно изменённые строки, даже скрытые фильтром. «Только изменённые», сброс
и просмотр плана доступны внизу. Группового назначения этот этап не добавляет.

Деньги в таблице форматируются только для отображения; точные исходные строки
сохраняются в полях/данных и серверном плане. Учтённый расход и остаток не означают
окончательный расход/гарантированный допуск. Недоступные данные и штатная блокировка
остаются заметными; технические подробности раскрываются по запросу.

Для автоматической отправки opaque-origin Rich UI сохраняются оба штатных шага:
подтверждение отправки из карточки в чат и серверное подтверждение свежего изменения.
Прямого авторизованного iframe→Tool RPC в pinned0.12.2 нет; same-origin или обход
проверки прав для сокращения модальных окон не включаются. Обновлённый helper
`employee_budget_admin_ui.py` должен быть загружен новым процессом WebUI при отдельно
разрешённой установке; одного совпадения неизменённого Tool source недостаточно.

Для просмотра месячного бюджета установить и включить Event `employee_budget_monthly_view`
через native Functions API, прочитать сохранённые source/type=`event`/`is_active=true`.
Новых module mounts и отдельного credential не требуется: Event использует уже
подключённые budget modules и common `ledger_base_url`/`ledger_admin_key`.

`GET /api/v1/employee-budgets/monthly` возвращает бюджет текущего native authenticated
user. Параметр `?user_id=<UUID>` другого сотрудника доступен только действующему
администратору. Роль и целевой пользователь повторно проверяются перед выдачей;
ответ `Cache-Control: no-store`. Клиенту не выдаются native key hashes, aliases и
management credentials. GET не создаёт назначений и не меняет финансовые данные.
Отсутствующая/противоречивая native конфигурация даёт безопасный отказ, не нулевой бюджет.

Суммы — строковые десятичные native counters и проекция cap-minus-spend; это не
гарантия допуска следующего запроса с учётом резервов. Период/следующий reset передаются
из native user/model полей без пересчёта календаря.
`expense_observation_scope=native_budget_counters` обозначает штатные counters;
чтение месячного бюджета и админской таблицы не требует исторических Usage witnesses.
Недоступные данные не превращаются в нулевой расход.

Личный GUI использует уже установленное действие **«Стоимость: детали»** у
собственного ответа. Оно показывает расходы ответа/чата и раздел **«Мой бюджет»**:
личный лимит, учтённый расход, остаток, native период/следующее обновление, данные
и блокировку по моделям. Повторное открытие читает свежий снимок. Для этого нужен
активный Event `employee_budget_monthly_view`; Action вызывает его серверный reader
с native пользователем, не передаёт ключи в iframe и не вызывает модель. Если
месячный reader недоступен, этот раздел явно недоступен; расходы ответа/чата
сохраняют самостоятельный результат. Ноль не подставляется вместо ошибки.

Это штатный снимок внутри сообщения: действие доступно у существующего собственного
ответа, отдельной страницы до первого ответа нет. При явной публикации/экспорте чата
пользователь публикует и сохранённый снимок; карточка сообщает об этом и не содержит
email/UUID сотрудника. Fresh self/admin read остаётся защищённым серверными правами.

OCR использует тот же common `service_payer_id` без зависимости от `target_model_id`
служебного Pipe; выбранная OCR-модель остаётся прежней. Это отдельная операция над
файлом, поэтому её расходы не добавляются к личной стоимости ответа/чата. В native
Responses 0.12.2 `TASK` может быть пустым: служебного плательщика разрешает только
проверенная подпись `document_ocr`, связанная с actor, File и точным model alias.
Произвольные body metadata, старый chat-service token без TASK и неподписанный вызов
такого разрешения не дают.

Все согласованные LLM connections, включая Responses, должны использовать общий
gateway bearer и native headers `X-OpenWebUI-User-Id: {{USER_ID}}`,
`X-OpenWebUI-Task: {{TASK}}`. Сохранить тип API, wire model IDs, полный контекст,
Tools и reasoning; изменение URL само по себе не доказывает совместимость.

Обычный `/api/chat/completions` с native API key и без сохранённого чата получает
от существующего Filter отдельную подписанную API operation. Владелец ключа
остаётся плательщиком; операция не становится выдуманным chat/message, не включает
чатовый вывод стоимости и не меняет историю/формат HTTP ответа. Используются те
же native assignments, лимиты и SpendLogs. Сведения о человеке
внутри1С из общего ключа не выводятся. Этот source candidate прошёл адресную и
независимую проверку; integrated runtime/реальная1С до приёмки не заявляются.

После установки сверить один согласованный сквозной сценарий с native ledger:
форма → запрос/помощник → две суммы → отказ → изменение лимита → восстановление;
known0/unknown, Details/reload и чужой доступ — в объёме принятой приёмки GOAL.

## Откат с сохранением данных

Остановить поступление новых managed model calls на время отката. Вернуть
сохранённые image/config/env и native Functions/Tools/Models/Valves/ACL, сверить
их точную идентичность. Native бюджеты, key assignments и SpendLogs сохранить;
не выполнять `down -v`, очистку Redis, прямую правку spend или импорт stand DB.
Восстанавливать DB из backup только отдельной согласованной процедурой, поскольку
обычный откат кода не должен стирать новые финансовые записи.

Возобновить трафик после проверки management доступа, учёта и enforcement на
согласованной конфигурации. Прежний прямой маршрут к провайдеру автоматически
не включать: режим работы при откате согласуется как часть deployment.
