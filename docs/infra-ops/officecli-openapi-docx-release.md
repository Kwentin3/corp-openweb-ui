# OfficeCLI в обычном чате OpenWebUI

Единственный пользовательский вход — обычный чат с выбранной прямой моделью.
Отдельный Office Documents, его промпт и маршруты обратной совместимости удалены
из целевой конфигурации. Историю чатов и пользовательские файлы не удалять и не
переписывать. Для продолжения старого чата пользователь выбирает доступную модель;
скрытая подмена удалённого профиля запрещена.

Этот runbook описывает выпущенный native-workflow. С 15.10.2026 рабочая версия —
OpenWebUI 0.12.2; точные образы, перенос данных, шлюз совместимости и границы
восстановления находятся в [актуальной инструкции](openwebui-0122-cutover.md).
Первоначальная приёмка Open Terminal зафиксирована в
[производственном отчёте](../reports/2026-09-28/open-terminal-production-acceptance.report.md).
История квалификации OfficeCLI приведена в
[отчёте кандидата](../reports/2026-09-28/officecli-native-kiss.report.md).
[Дополнение для заказчика](../commercial/COMPLETED_WORK_2026-09-28_OPEN_TERMINAL_OFFICE_WORKFLOW.md)
описывает тот же выпуск без операционных деталей.
Наличие более нового кода в Git само по себе не означает его выкладку: при
сопровождении сверять установленный release-state и фактические образы.

## Владельцы и конфигурация

- OpenWebUI владеет пользователями, чатами, правами, файлами и вложениями.
- Установленный OfficeCLI владеет командами, синтаксисом, проверками и справкой.
- Существующий OpenAPI-адаптер переводит только транспорт файлов и ограничивает
  ресурсы. Он не выбирает содержание документа или бизнес-сценарий.

В **Admin Settings → Integrations → Tool Servers** используется один сервер:

- ID `officecli`, URL `http://officecli-0122:8080` во внутренней сети выпуска 0.12.2;
- авторизация `Session`, штатные access grants авторизованных пользователей;
- соединение включено, отдельные назначения инструмента офисным профилям не нужны.

Единственный автоподключающий слой — Function из
`deploy/openwebui-functions/officecli_auto_attach_filter.py`. Импортировать точный
source выбранного коммита, сверить LF SHA-256 и версию. Используются штатные
независимые переключатели **Active** и **Global**. Вторых копий и резервных
Functions в реестре приложения не держать.

`target_model_ids` содержит разрешённые прямые модели. Исходный список берётся из
`DEFAULT_TARGET_MODEL_IDS` этого же файла; не вести его дубликат в runbook.
При выпуске сверять с фактическим каталогом и сохранять действующие права доступа.
Пустой список выключает автоподключение. Удалённые профили не добавлять.
NDFL/Broker/STT, task models и провайдеры без native tool calling не включать.
Действующие Valves в реестре приложения имеют приоритет над исходными defaults:
не заменять их списком из source при добавлении одной модели. Сравнивать
`/api/models` под обычным пользователем с установленным `target_model_ids`;
административный каталог и активные сохранённые профили сами по себе не
доказывают доступность модели пользователю. Для совместимого пропуска достаточно
добавить точный ID через штатные Valves существующего Filter, сохранив остальные
значения, Active/Global, Tool Server и grants. После readback проверить обычный
чат и итоговые файлы. Образ, core и отдельный модельный маршрут для этого не нужны.
Аудит охвата от 23.10.2026 находится в
[отчёте подключения моделей](../reports/2026-10-23/office-model-coverage.report.md).
На приёмке 15.10.2026 OfficeCLI выполнили все десять текстовых моделей,
доступных проверочному обычному пользователю. Девять выполнили точный запрос
сразу, Gemini 3.1 Flash Lite — после исправления параметра. Административная
видимость других моделей не означает публичную квалификацию; действующий
каталог и права остаются в штатной конфигурации OpenWebUI.

Filter выбирает native function calling до штатного разрешения `tool_ids`.
Вспомогательные tasks и запросы с явно переданными `tools` остаются у своего
владельца. Права сервера и файлов проверяются OpenWebUI, Filter их не обходит.

`no_reasoning_model_ids` отражает проверенное ограничение текущего провайдера
Chat Completions. Явно выбранный несовместимый reasoning приводит к ошибке,
а не скрытому снижению. Смена провайдера или протокола не выполняется автоматически.

Для `gpt-6-luna` производственный маршрут переведён на существующее подключение
Responses через штатную настройку Connections: ID добавлен в его `model_ids`,
а из действующего `no_reasoning_model_ids` удалён только этот ID. Остальные
подключения, ключи и исключения сохранены. Дефолт Valve остаётся совместимостью
для Chat Completions; при смене API администратор сверяет действующее значение.
`reasoning_effort=none` в запрос Responses не передаётся: используется штатное
значение reasoning модели. Stateful-хранение у провайдера не требуется.
См. [контракт модели](https://developers.openai.com/api/docs/models/gpt-6-luna).

В текущем образе 0.12.2 применена
[адаптация передачи контекста](../../deploy/openwebui-patches/tool-context-v0.12.2/README.md).
Порядок истории исправлен самим OpenWebUI; старый пакет 0.11.4 поверх новой
версии не применяется. Существующие Chat Completions-подключения используют
один внутренний LiteLLM, описанный в актуальной инструкции выпуска.
Для Responses предпросмотр остаётся результатом вызова инструмента. Для Chat
Completions сохраняется штатное представление OpenWebUI: картинки результата
могут переноситься в следующую служебную user-реплику. Различие транспортных
представлений проверяется отдельно от качества текста готового документа.
Stateless Responses также сохраняет зашифрованные reasoning-блоки между
инструментами через существующий конвертер провайдера. При смене модели
привязанные к прежней модели данные снимает штатная проверка идентичности.
Обычный Chat Completions эти блоки не получает. Отдельный провайдер, клиент
LLM, цикл выполнения или stateful-хранение для этого не добавляются.
Завершившийся ответ и успешный `validate` не подтверждают отсутствие смысловых
пропусков: при приёмке нужен полный текст результата и сверка с источником.

Создание нового содержания и оформление готового ответа разделены в контракте
инструментов. `create_office_document` составляет новый документ;
`export_answer_to_word` импортирует предыдущий готовый ответ целиком, по умолчанию
`source_message: "previous_assistant"`. Существующий клиент OpenWebUI находит
завершённый ответ через parent IDs текущего хода и читает его с сессией вызывающего
пользователя. OfficeCLI импортирует полный Markdown напрямую; команды модели
задают оформление и дополнительные запрошенные поля. Перед публикацией
проверяются весь текст абзацев, их порядок и отсутствие повторного импорта;
повторное чтение native source обнаруживает его изменение во время операции.
Receipt содержит ID источника, SHA-256 исходного текста и результат проверки.
Этот контракт относится к созданию DOCX; после последующих правок отдельно
сверяй конечный файл. Обе операции используют один исполнитель DOCX и native Files.

Кандидат 23.10.2026, до отдельной runtime-приёмки: тот же `export_answer_to_word`
поддерживает сохранённую заметку через `source_note_id`. При этом `source_message`
нужно опустить; `commands` можно опустить, чтобы импортировать весь текст без
переписывания моделью. Адаптер читает `data.content.md` штатным
`GET /api/v1/notes/{id}` с сессией пользователя и повторно читает источник перед
публикацией. При отказе в доступе, несовпадении ID, пустом Markdown или изменении
источника файл не публикуется. Receipt различает `source_note_id` и
`source_message_id`. Путь прежних ответов и Action остаётся прежним.
Текущий статус и полная матрица находятся в
[продуктовом отчёте](../reports/2026-10-23/proposal-docx-product-acceptance.report.md).

Тот же кандидат ограничивает браузерное состояние временем одного CLI-вызова.
Существующий nonresident-исполнитель создаёт собственный временный каталог,
передаёт его через `XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, `TMPDIR`/`TMP`/`TEMP`
и очищает после завершения принадлежащих вызову процессов. Общий `HOME` и
лимит `/tmp` не увеличиваются. Это устраняет накопление scoped-профилей Chromium
между рендерами; проверка PNG перед выдачей сохраняется. При выпуске новый
контейнер получает чистый tmpfs; отдельная фоновая очистка не нужна.

Для зафиксированного текста используется штатная Action
`deploy/openwebui-functions/officecli_word_export_action.py`: **В Word** или
**Word: дата и подписи** под выбранным завершённым ответом. Она вызывает тот же
`export_answer_to_word` через native `get_tools`, передавая ID выбранного сообщения
и `source_message: "selected_assistant"`. Текст из тела browser request не считается
источником; его заново читает существующий клиент с сессией пользователя.
Файлы прикрепляются штатным API к выбранному ответу, сам текст не переписывается.
Экспорт не вызывает LLM и не добавляет отдельный renderer, provider или хранилище.
Исследованные необязательный и обязательный выбор источника самой моделью не
обеспечили устойчивого сохранения текста. Для обычной просьбы оформления отдельная
операция экспорта явно отличает сохранение ответа от составления нового содержания;
её приёмка требует повторов через обычный чат. Кнопка остаётся дополнительным путём.
Два автономных агента для этого не требуются.

OfficeCLI запускает каждый нерезидентный вызов в отдельной POSIX-группе
процессов и завершает всю группу при выходе или тайм-ауте. Сервис использует
штатный Docker `init: true`, который подбирает завершившихся потомков.
Это устраняет утечку Chromium после тайм-аута: старый исполнитель завершал
только CLI, оставляя браузеры и занятые ими PID. Лимит PID не повышается.
Проверять нужно реальные процессы после повторного рендера и принудительного
тайм-аута; здоровый HTTP endpoint сам по себе не доказывает их отсутствие.

## Добавление и замена модели: обязательный чек-лист

Применять при публикации новой пользовательской текстовой модели, смене её
точного ID, провайдера или API. Задача считается завершённой, когда записаны
результат офисной проверки либо обоснованное исключение и доступные пользователю
ограничения. Наличие модели в каталоге само по себе не подтверждает готовность
её Office-возможностей. Этот порядок выполняет сопровождающий при изменении
каталога; автоматическое обнаружение моделей не внедрено.

1. **Установить маршрут и исходное состояние.** Сверить точный ID в `/api/models`
   под обычным пользователем, фактические провайдер и API, поддержку native
   function calling и выбранного reasoning. Сохранить версию OpenWebUI,
   версию/хеш Filter, Valves, Active/Global, подключение OfficeCLI и grants.
   Флаги карточки и Action «В Word» не подтверждают подключение инструментов модели.
2. **Подготовить минимальное изменение.** Для совместимого пропуска добавить
   только точный ID в действующие Valves существующего Filter. Сохранить остальные
   значения и набор для отката; ограничения reasoning менять только по доказанному
   требованию провайдера/API. Для несовместимой или недоступной пользователю модели
   записать причину исключения, сохранив прежние права.
3. **Проверить настройку и применить.** До внешнего прогона исполнить окончательные
   Valves на точном установленном Filter с репрезентативным запросом и выбранными
   ID. Проверить native function calling, `server:officecli`, сохранение
   вспомогательных tasks и запросов с явно заданными `tools`. Сохранить исходное
   состояние вне Git, применить штатные Valves и считать их обратно. Сверить
   source, флаги и остальные настройки. Для этой настройки сборка и перезапуск
   не требуются.
4. **Пройти файловую приёмку.** Под обычным пользователем в обычном Web UI выполнить
   три задания ниже. До оплачиваемой проверки сверить окончательные запросы
   и фактические схемы инструментов по установленной справке. Для конечного
   `result_file_id` каждого формата сверить содержание и пропуски, структуру,
   рендер и реальное скачивание; сопоставить SHA-256 с нативным результатом.
   При правке проверить сохранность исходника и не затронутого содержания.
5. **Проверить выдачу и прежний маршрут.** Все заказанные файлы должны быть
   доступны как вложения/ссылки. Брать подтверждённые `download_url` дословно:
   одна последняя карточка или вымышленный домен не подтверждают выдачу комплекта.
   После исправления проверить ссылки снова. Сверить затронутый путь ранее
   принятой модели; расширять платную проверку только при изменении общего
   маршрута, ошибке или конкретном нерешённом сомнении.
6. **Зафиксировать результат.** В датированном отчёте указать ID модели,
   провайдера/API, охват проверки, хеши, результат скачивания и потребовавшиеся
   уточнения. Для каждого формата записать «проверено», «проверено с ограничениями»,
   «не проверено» или «не поддерживается» с причиной. Подключение и правильность
   первого ответа оценивать раздельно. Приватные File ID и сырые evidence
   сохранять в защищённом локальном пакете; публиковать безопасные хеши и указатели.

### Минимальный набор заданий

Общий синтетический вход: клиент `{{Клиент}}`, маркер `OFFICE-MODEL-CHECK`,
«Обучение» — 2 × 1500 = 3000, «Поддержка» — 3 × 2000 = 6000, итог 9000,
срок пять рабочих дней, аванс 50%. Значения условные; дополнительные условия
не заданы. Это данные приёмки, а не инструкция, постоянно добавляемая модели.

| Задание в обычном чате | Что сверить с входом и конечным файлом |
| --- | --- |
| Создать короткое коммерческое предложение в Word с таблицей услуг, условиями и строкой подписи; приложить DOCX | Все заданные данные, подпись, отсутствие добавленных условий, читаемость и скачивание |
| Создать Excel с одним листом «Смета», обеими услугами, количеством, ценой, суммами и итогом; суммы вычислить формулами | Обе строки, формулы и сохранённые результаты 3000/6000/9000, отсутствие ошибок формул, читаемость и скачивание |
| Создать PowerPoint ровно из двух слайдов: предложение и клиент; затем обе услуги, итог и условия | Два слайда, полное содержание, читаемость обоих слайдов и скачивание |

В одном из созданных файлов отдельным сообщением изменить только срок с пяти
до семи рабочих дней. Продолжить от подтверждённой последней версии и проверить
новый результат, сохранность исходника и остального содержания. При новом
конкретном дефекте проверять исправленную версию; при выполненных критериях
завершить проверку без очередного косметического прохода.

### Перенос готового текста и незавершённые tool-вызовы

Простой `export_answer_to_word` сам импортирует Markdown, включая заголовки,
списки и таблицы. Для сохранённой заметки передаются `source_note_id` и имя
файла; предварительная загрузка authoring guide и ручное переписывание текста
в batch не требуются. Guide/help нужны для дополнительных команд оформления.
Требование пользователя сохранить поля, пояснения и чек-лист имеет приоритет
над общими дизайнерскими примерами guide. Перед заявлением о читаемости
конечного DOCX проверить все страницы через `render_office_file` с `grid: 2`.

Для инцидента с уже подготовленным текстом дополнительно повторить именно
исходный продуктовый сценарий. У короткого нового документа и полного переноса
заметки разные критерии: сверить все разделы, таблицы по ячейкам, поля,
пояснения, порядок и дубликаты с полным источником. Обе стороны сравнения
считывать независимо от заверения модели. Строковые переводы Word (`w:br`) и
табуляция являются разделителями, а чекбокс может отображаться символом `☐`.
Разрешённое преобразование разметки не оправдывает пропуски или новые условия.

Использовать существующий путь. Готовый ответ ассистента переносит
`export_answer_to_word`; полный Markdown прочитанной заметки принимает
нативный `add` типа `markdown` через `props.markdown` в `create_office_document`.
Заметка не является предыдущим ответом ассистента. Не создавать второй экспортёр
или промежуточную копию ответа в истории ради выбора этого источника.
Create/apply уже управляют жизненным циклом файла; допустимые batch-команды,
поля и лимиты брать из установленной справки и OpenAPI. Придуманный `/tmp`-путь
не становится существующим источником файла.

Успешно прочитанный skill, наличие tools и пустой завершённый ответ без
`result_file_id` не подтверждают выполнение. Сохранять неуспешный первый прогон
и результат продолжения раздельно. Если понадобились ручные подсказки с CLI-
командами, не называть это самостоятельным прохождением исходного запроса.
Ошибку параметров инструмента, отказ занятого рендера, завершение модели без
результата и ошибку транспорта исследовать раздельно; HTTP 200 провайдера
сам по себе не устанавливает причину пустого ответа. При таком сбое выполнить
ограниченный повтор в чистом чате и исследовать фактический маршрут до правки
общих настроек или инструкций.

Если Office не проверен или не поддерживается, при публикации модели явно
обозначить это ограничение. При смене ID, провайдера или API прежний результат
не переносится автоматически: повторить затронутую проверку. Действующий
`target_model_ids` остаётся единственным владельцем разрешённого набора;
датированные отчёты фиксируют результаты проверок, а не заменяют настройку.
При ошибке подключения вернуть только затронутые Valves, сверив отсутствие
новых независимых изменений; файлы и историю сохранить.
Пример разделения подключения, файловой приёмки и ограничений —
[аудит от 23.10.2026](../reports/2026-10-23/office-model-coverage.report.md).

## Контекст и выполнение

Описание `get_officecli_help` содержит неизменённый workflow из `tools/list`
установленного OfficeCLI. Подробные skills и адресный help загружаются по запросу.
Источник общего транспортного контекста — `OFFICECLI_INSTRUCTION` в Filter;
не копировать его в промпты моделей и не добавлять инструкции по отдельным заданиям.

Штатный файловый контекст передаёт ID вложений и восстанавливает их из истории.
При нескольких источниках агент передаёт явный `file_id`; неоднозначность должна
возвращаться ошибкой. Текстовые цитаты RAG не заменяют исследование структуры.
Настройка File Context остаётся у OpenWebUI; её глобальное отключение не входит
в этот выпуск. Результаты сравнительных прогонов приведены в отчёте.

Чтение не публикует файлы. Create/apply работают с копией и возвращают штатные
`result_file_id` и `download_url`. Nonresident CLI сохраняет результат до ответа;
отдельные open/save/close не нужны. Частичный результат после ошибки не публикуется.
Ответ должен показывать реальное вложение, а не вымышленную sandbox-ссылку.

Большие чтения имеют продолжение `next_offset` / `next_text_offset`. Ограничения
пакетов и рендеринга опубликованы в OpenAPI; автоматического дробления, best-effort
или замены команды другим движком нет. Сценарный сборщик Excel и автоматическая
нормализация Word удалены. Нативный `merge` — подстановка шаблона, не обещание
произвольного переноса книг без потерь.

### Завершение многоэтапной работы

Универсальная инструкция находится в
[`deploy/openwebui-skills/artifact-workflow.md`](../../deploy/openwebui-skills/artifact-workflow.md).
Она установлена как штатный Skill и использует native Tasks для перечня частей,
прогресса и проверки. Не дублировать её в системных промптах моделей. Один план
не обеспечивает перенос большого массива данных: полный Excel-прогон завершился
после подключения штатного Open Terminal с серверным Linux-выполнением.

Open Terminal подключён через штатный раздел Integrations. На проверенной 0.9.6
Tool `terminal_file_transfer` передаёт явно выбранное и разрешённое вложение чата
в новую рабочую папку и публикует проверенный результат обратно в OpenWebUI Files.
Файл, оставшийся только в рабочей папке Terminal, не является вложением чата.
Права Tool, Skill и Terminal выданы всем пользователям после отдельного принятия
границы доверенной команды. Два обычных пользователя получили разные домашние
каталоги; общий контейнер не считается изоляцией взаимно недоверенных арендаторов.

Кандидат операции `render_office_file` принимает `grid` для обзора всех страниц
DOCX или слайдов PPTX. Для проверки пагинации Word использовать этот штатный
режим: в закреплённом OfficeCLI одиночная первая страница пропускает пагинацию и
может показывать ложный перенос/наложение. Отдельные страницы остаются для деталей.
Не повторять изменения документа ради дефекта, который исчезает при проверке
того же файла другим штатным режимом просмотра.

Кандидат Filter исправляет только добавленный моделью префикс `sandbox:` у
Markdown-ссылки, если её адрес и ID подтверждены успешным результатом публикации
OfficeCLI в текущем ответе. Неизвестные адреса не восстанавливаются по имени файла.
Это не универсальная защита от вымышленных ссылок. Границы проверки и внедрения
описаны в [отчёте кандидата](../reports/2026-09-28/office-workflow-completion.report.md).

### Передача файлов в Linux

Для установленной OpenWebUI 0.9.6
`deploy/openwebui-tools/terminal_file_transfer.py` связывает существующие Files API,
выбранный Terminal и события вложений. `stage_chat_file` копирует доступное
вложение в новую папку; `publish_terminal_file` сохраняет новый результат в Files
и прикрепляет его к ответу. Исходники сохраняются. Содержимое файлов и секреты
не передаются через контекст модели. Временное чтение повторяется один раз;
операция записи автоматически не повторяется.

До выпуска обычный чат с двумя исходными книгами прошёл полный путь на Linux:
23 листа, все значения и изображения, публикация самим агентом. После выпуска
отдельный обычный пользователь прошёл XLSX, DOCX и PPTX через передачу, Linux-
обработку и штатную публикацию; исходные хэши сохранились. Tool, Skill и Terminal
включены для всех пользователей только на разрешённых прямых моделях и только при
наличии Office-вложения. Обновление всей платформы ради более нового Filesystem
upload требует своей проверки существующих расширений. Подробности — в
[отчёте передачи файлов](../reports/2026-09-28/terminal-file-handoff.report.md) и
[производственной приёмке](../reports/2026-09-28/open-terminal-production-acceptance.report.md).

Общий OpenWebUI-слой устанавливается скриптом
`deploy/openwebui-tools/office_workflow_release.py`. Он принимает два файла с
правами `0600`: короткоживущий admin token и полное описание уже выбранного
Terminal-соединения. При `apply` порядок фиксирован: Terminal → Tool → Skill →
глобальный Filter. До последнего шага пользовательский маршрут не переключается.
Скрипт создаёт новый файл отката через exclusive create с правами `0600`; там
находится прежняя конфигурация, включая прежний секрет соединения, поэтому этот
файл нельзя класть в Git или выводить в журнал.

```bash
python deploy/openwebui-tools/office_workflow_release.py apply \
  --base-url http://openwebui:8080 \
  --token-file /run/secrets/openwebui-admin-token \
  --terminal-connection-file /run/secrets/office-terminal-connection.json \
  --backup-file /release-state/office-linux-before.json
```

Откат использует тот же base URL и token, но не принимает новое соединение:

```bash
python deploy/openwebui-tools/office_workflow_release.py rollback \
  --base-url http://openwebui:8080 \
  --token-file /run/secrets/openwebui-admin-token \
  --backup-file /release-state/office-linux-before.json
```

### Trusted-team Open Terminal runtime

`compose/open-terminal-office.compose.yml` is the accepted runtime after explicit
confirmation that every current OpenWebUI user is trusted at the same level. It
enables upstream multi-user mode and separate homes, keeps the service off host
ports, pins the qualified full image, and joins only `openwebui_web`. The shared
kernel, process list, network, root-capable system state and 2 GiB resource pool
are not per-user isolation.

Keep `OPEN_TERMINAL_API_KEY` in a server-local mode-0600 environment file. Build
the release connection file with ID `office-linux`, URL
`http://open-terminal-office:8000`, `auth_type` `bearer`, the same key,
`config.enable=true`, and the `user:*:read` grant. Keep that JSON mode 0600 and
pass it to `office_workflow_release.py apply`; do not print either file.

Apply in this order:

1. Start the pinned Compose service and wait for its Docker health status.
2. Add `open-terminal-office` and `open-terminal-office:8000` to both `NO_PROXY`
   and `no_proxy` for OpenWebUI. Without this entry the outbound proxy can return
   HTTP 502 for the internal Terminal route.
3. Run the common release installer. It switches the global Filter last.
4. Run an ordinary-user Office chat, then a second synthetic-user separation
   check without private files.
5. Verify OpenWebUI health, public HTTP, container restart counts, result
   attachment download and unchanged source hashes.

Rollback starts with `office_workflow_release.py rollback`, then stops the
Compose service. Do not pass `--volumes` to `docker compose down`; the named home
volume is preserved for a reviewed recovery or later deletion.

For users who must be protected from one another, do not use this Compose file.
Deploy licensed Terminals and pass its already qualified connection JSON to the
same common installer. The Kubernetes backend plus NetworkPolicy is the upstream
path when network isolation is required.

Откат возвращает старый Filter первым, затем восстанавливает или удаляет только
ресурсы с ID `terminal_file_transfer`, `artifact-workflow` и `office-linux`.
Другие Terminal-соединения, включая добавленные после выпуска, сохраняются.

## Установка и выпуск

1. Использовать существующий OpenWebUI и сеть `openwebui_web`. Ядро, volume и
   пользовательские данные не пересоздавать. Подтверждённая адаптация протокола
   Google находится в `deploy/openwebui-patches`; это не альтернативный tool loop.
   Удалять её после квалификации штатной поддержки на выбранном runtime.
2. Собрать sidecar из `services/officecli-openapi-proof/Dockerfile` и Compose
   `compose/officecli-openapi-proof.compose.yml`. Закрепить точный image ID, сверить
   source, отсутствие host ports, read-only root, tmpfs и внутреннюю сеть.
3. Проверить CI, реальный установленный CLI и обычный пользовательский чат.
   Сверить структуру и содержимое скачанных XLSX/DOCX/PPTX, формулы, сохранность
   исходников, read-only запрос, follow-up, reload и смену модели. Отсутствие доступа
   к провайдеру записывать как непроверенный пункт, не как успешный тест.
4. Удалить Workspace Model `office-documents` штатным Models API, убрать его ID из
   valves. Удалить отключённые резервные OfficeCLI Functions. Не создавать алиас,
   перенаправление или fallback для старого ID. Перед и после сверить сохранность
   истории и файлов; не вызывать маршруты удаления чатов или файлов.
5. После согласованного выпуска обновить единственный sidecar и единственную
   Function. Обновить кеш схемы штатным сохранением существующего Tool Server:
   `GET /api/v1/configs/tool_servers`, затем `POST` неизменённой конфигурации.
   Сохранить ID, Session auth и права. Не добавлять второй публичный сервер.

   Для доставки образа без сборки на production доступен штатный ручной запуск
   Active CI на точном commit с `export_officecli_image=true`. Только после
   успешных проверок реального CLI workflow сохраняет `officecli-runtime-<sha>`:
   Docker archive, точный image ID, source commit и `SHA256SUMS`. Перед `docker load`
   сверить суммы и commit, затем закрепить полученный image ID у существующего
   sidecar. Экспорт выключен по умолчанию; production VPS не используется
   для чистой сборки или репетиции.
6. Повторить обычный пользовательский путь на установленной версии. Удалить
   временные QA-профили, Functions и соединения после завершения их назначения.

При сбое выключить **Active** у общей Function и при необходимости остановить
только sidecar. Не переключать пользователей на старую модель, промпт или сборщик.
Исправленный кандидат проходит те же проверки перед повторным включением.
Архивные образы и отчёты являются forensic evidence, а не активным fallback.

Для инцидентов использовать существующий [самописец](openwebui-flight-recorder.md),
сопоставляя container ID, UTC и фактическую ошибку. Не выводить причину OOM только
из совпадения по времени с вызовом инструмента.
