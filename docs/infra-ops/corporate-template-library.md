# Корпоративные DOCX-шаблоны через native Skills и Knowledge

Инструкция описывает установленный пилот для OpenWebUI 0.12.2, поставленный
через [PR #581](https://github.com/Kwentin3/corp-openweb-ui/pull/581).
Сотрудник выбирает профиль **«Корпоративные документы»**; администратор готовит
и публикует шаблоны через **«Подготовка корпоративных шаблонов»**.

Целевая конфигурация: постоянная библиотека доступна на чтение всем сотрудникам;
публиковать в неё могут только администраторы. Роли и группы технической QA-проверки
не определяют бизнес-права библиотеки.

## Проверенный срез на 30 октября 2026

Принят один DOCX-шаблон договора разовых работ с одной позицией спецификации:
71 поле, 42 группы входных данных, 27 групп с повторениями. Проверены подготовка
и явная публикация из авторского чата, поиск другим пользователем без вложения
или выбора Skill, сбор данных, передача полного Skill и фактов Terra/OfficeCLI
и скачивание заполненной копии через обычный UI. Точные скачанные байты прошли
сверку XML, всех значений и оформления; Microsoft Word сохранил значения после
обновления полей. Все четыре страницы проверены визуально.

Полное заполнение проверялось на отдельных QA-пользователях. После переноса в
постоянную библиотеку **«Корпоративные шаблоны»** проверены идентичность оригинала
и настроек, штатные права и поиск из обычного чата сотрудника. Полное заполнение
на постоянном alias повторно не запускалось. Чтение доступно сотрудникам,
публикация и изменение библиотеки — администраторам; неавторизованный доступ
отклоняется. 32 тестовых ресурса удалены, capture выключен, все 24 референса
сохранены без изменений. Частные документы и диагностические payloads в Git
не включены.

Ограничение: индивидуальные страницы предпросмотра OfficeCLI могут расходиться
с его монтажом и Microsoft Word по пагинации и колонтитулам. Renderer не
исправлялся; принята именно скачанная копия, проверенная в Word оператором.
У worker нет Word runtime. Другие шаблоны, несколько позиций спецификации
и юридическая корректность этой проверкой не принимаются.

## Владельцы и поставляемые компоненты

- Native Skill хранит назначение шаблона, описание для поиска, группы входных
  данных, карту полей, правила заполнения и проверки. В нём только `SKILL.md`.
- Native Files/Storage хранит отдельный оригинальный DOCX. Knowledge связывает
  его точный File ID с читателями через штатные access grants.
- [Авторский Skill](../../deploy/openwebui-skills/corporate-template-authoring.md)
  описывает подготовку и согласование документа средствами OfficeCLI.
- [Publication Tool](../../deploy/openwebui-tools/corporate_templates.py) имеет
  одну операцию `publish_template(skill_id, file_id)`: связывает существующий
  файл с настроенной Knowledge и публикует инструкцию для её READ-аудитории.
  Он не копирует бинарный файл и не хранит собственный реестр.
- [Native model export](../../deploy/openwebui-tools/corporate_template_models.json)
  задаёт административного автора, ведущую модель и фиксированный Terra worker
  для OfficeCLI. Все три профиля используют существующий `gpt-6.1-terra`;
  публикация не создаёт клиента провайдера или собственного исполнителя.

Эта capability использует native Tools, Skills, Knowledge, Files и ACL; новых
изменений ядра для неё нет. Существующие адаптации конкретного выпуска описаны
в [инструкции 0.12.2](openwebui-0122-cutover.md). Рабочий OfficeCLI-маршрут и
его владельцы описаны в [OfficeCLI runbook](officecli-openapi-docx-release.md).

## Установка и предварительная конфигурация

Пользовательская инструкция находится в
[docs/commercial/CORPORATE_DOCUMENTS_USER_GUIDE.md](../commercial/CORPORATE_DOCUMENTS_USER_GUIDE.md).
Её источник — этот файл в Git. Для помощи в чате публикуется native Skill
`corporate-documents-help` с названием «Помощь: корпоративные документы»:
содержимое `SKILL.md` в точности повторяет пользовательскую инструкцию,
description описывает вопросы о пользовании, профилях, библиотеке и публикации.
Skill активен, admin-owned, имеет только `user:*` READ; отдельный DOCX или
запись Knowledge для текстовой справки не нужны.

При изменении инструкции обновить её опубликованную копию штатным редактором
или API Skills с проверкой текущей версии. После публикации перечитать содержимое
и сравнить его с источником; путь исходника, сохранённую версию Skill и SHA-256
UTF-8-текста зафиксировать в квитанции обновления. Произвольные поля
`source_path` и `source_sha256` в native metadata этого выпуска не сохраняются.
Нового сервиса синхронизации нет. Проверка справки:
обычный пользователь спрашивает, как пользоваться шаблонами; агент читает
справочный Skill, объясняет порядок работы и ограничения без делегирования
или создания файла. Запрос на заполнение проверяется отдельно: он должен
по-прежнему выбирать инструкцию самого шаблона и собирать реквизиты.

1. Сверить установленную версию, образ и исходники с принятым выпуском.
   Контракты публикации проверялись на upstream 0.12.2, commit
   `6a18585ff4c2e5f6805f682222cfbc46dc669ef8`; один номер версии не доказывает
   идентичность установленного образа.
2. Создать обычную внутреннюю Knowledge для библиотеки. Дать всем сотрудникам
   READ, WRITE оставить только администраторам. Если все authenticated users
   инстанса являются сотрудниками, использовать native `user:*` READ; если есть
   внешние пользователи, использовать штатную группу сотрудников. Не использовать
   внешнюю read-only Knowledge.
   Зафиксировать её ID и проверить сохранённые grants обычными пользователями.
3. Администратору импортировать точный source `corporate_templates.py` как
   Workspace Tool. Ограничить его использование администраторами, без общего
   READ-grant сотрудникам; при необходимости явно назначить штатную группу
   администраторов. Подключить к административному авторскому модельному маршруту
   через штатные настройки. Сверить сохранённые
   source/hash, схему единственной операции и access grants.
4. В Valves указать `knowledge_id` этой библиотеки и `openwebui_base_url` —
   доверенный внутренний origin именно этого OpenWebUI, доступный из процесса
   Tool. Default `http://127.0.0.1:8080` требует проверки в целевой среде.
   Не подставлять внешний произвольный URL: Tool передаёт текущую пользовательскую
   сессию. Отдельного административного токена в Valves нет.
5. Установить авторский Skill из указанного Markdown через штатный импорт или
   редактор Skills, сохранив name/description и текст. Сделать его активным,
   выдать READ администраторам и проверить, что он содержит только `SKILL.md`.
6. Проверить административный доступ к native `create_skill`, изменение Skill
   и Knowledge и доступ к исходному File. Native API отдельно регулирует
   `workspace.skills`, `workspace.knowledge`, `access_grants.allow_users`,
   `access_grants.allow_groups`, `sharing.public_skills` и
   `sharing.public_knowledge` для неадминистративных ролей. Это не повод выдавать
   сотрудникам права публикации. Проверять сохранённые grants, а не только
   HTTP 200; у библиотечных Skills READ-аудитория должна совпадать с Knowledge.
7. Проверить текущий фиксированный worker, доступ читателя к нему и к OfficeCLI,
   native function calling, допустимые лимиты и сохранение результата в Files.
   Не считать наличие модели или административную видимость квалификацией
   рабочего маршрута обычного пользователя.

### Три native-профиля и фиксированный worker

Администратору импортировать
[corporate_template_models.json](../../deploy/openwebui-tools/corporate_template_models.json)
через Workspace Models. Файл имеет native export-форму: массив трёх моделей.
Для штатного `POST /api/v1/models/import` передать этот массив в поле `models`
объекта JSON. Импорт назначает владельцем текущего администратора; исходный
`user_id`, QA IDs и данные конкретного шаблона в файле отсутствуют. До импорта
проверить совпадения ID: native import может обновлять существующие записи.

- `corporate-template-author`: admin-owned, `access_grants=[]`; Tools
  `corporate_template_publication` и `server:officecli`.
- `corporate-documents`: READ для `user:*`; только
  `corporate_document_delegation` и native Skills/Files/Knowledge.
- `corporate-office-worker`: READ для `user:*`; только `server:officecli`.

У всех `function_calling=native`; у автора и worker `max_tokens=6000`,
у ведущей модели `max_tokens=12000` для полного пакета делегирования. Legacy
`reasoning_effort` не задаётся. Инструкции и переключатели повторяют проверенные
QA-профили; для нового Skill требуется уникальный понятный slug.
Оригинал и инструкции конкретного шаблона публикуются отдельно. Readable active
Skills обнаруживаются штатно, explicit `skillIds` в профилях не нужны.

Publication Tool импортировать с ID `corporate_template_publication`.
Community Tool импортировать с ID `corporate_document_delegation` из
[Skyzi000/open-webui-extensions](https://github.com/Skyzi000/open-webui-extensions),
commit `63310704483845c46b9ddbb65885f70938ac909e`, файл
[`tools/sub_agent.py`](https://github.com/Skyzi000/open-webui-extensions/blob/63310704483845c46b9ddbb65885f70938ac909e/tools/sub_agent.py).
SHA-256 точного файла:
`790de1a09eea5467ad7f87568f20c00099f7ca8c8ef1b946e55799d742c45fbe`.
Исходник community Tool в этой поставке не дублируется. Выдать ему READ для
`user:*`; публикацию оставить admin-only.

В Valves community Tool сохранить параметры проверенного маршрута:

```json
{
  "DEFAULT_MODEL": "corporate-office-worker",
  "AVAILABLE_TOOL_IDS": "server:officecli",
  "EXCLUDED_TOOL_IDS": "",
  "MAX_ITERATIONS": 12,
  "MAX_PARALLEL_AGENTS": 1,
  "APPLY_INLET_FILTERS": true,
  "ENABLE_CONTEXT_COMPACTION": false,
  "LARGE_TOOL_RESULT_MODE": "raw",
  "ITERATION_NOTE_ROLE": "user",
  "DEBUG": false,
  "ENABLE_FILE_TOOLS": true,
  "ENABLE_KNOWLEDGE_TOOLS": true,
  "ENABLE_SKILLS_TOOLS": true
}
```

Все остальные `ENABLE_*_TOOLS` выключить, включая `ENABLE_SKILLS_WRITE_TOOLS`
и `ENABLE_SUBAGENT_TOOLS`. Не включать глобальные native subagents и не менять
провайдеры, прямые модельные профили или глобальный OfficeCLI filter. Worker
должен получить все согласованные факты, требования и полный прочитанный текст
Skill verbatim, включая карту полей и exact paths, через пакет делегирования.
Передать фактически полученные ID/version Skill, без выдуманной версии, и
подтверждённый native File ID оригинала. Один Skill ID не переносит инструкцию;
native Skill tools у child могут отсутствовать. Проверенную карту exact XPath
из Skill можно использовать после сверки её привязки к точному оригиналу и SHA,
без повторного извлечения всего raw XML при каждом заполнении. Manifest в
контексте ведущей модели сам по себе не доказывает наличие инструкции у child.
Недоступность отдельной внешней проверки Word нужно честно указать при возврате
изготовленной копии; нельзя объявлять такую проверку пройденной или только из-за
её недоступности прекращать заполнение. После настройки
прочитать обратно профили, grants и Valves. JSON и успешный импорт не доказывают
работоспособность постоянного маршрута: его проверяют обычным пользовательским
чатом, фактическим контекстом worker и скачанным DOCX.

Оригинал администратор готовит и публикует от своего пользователя: native обработка
файла проверяет WRITE, даже если внешний add-file endpoint допускает READ.
Сотрудникам WRITE на библиотеку, исходный файл и опубликованный Skill не нужен,
а publishing Tool им недоступен. Ограничение публикации задаёт native ACL Tool
и Knowledge; исходный код адаптера не вводит собственную ролевую модель.
Владелец и администратор остаются исключениями ACL; проверочный запрещённый
пользователь должен быть обычным пользователем без других путей доступа.

## Автор: подготовка и явная публикация

1. В обычном сохранённом чате загрузить исходный DOCX. По авторскому Skill
   исследовать весь документ и согласовать поля, повторы, константы и изменения.
   Сохранить работоспособные Word form fields; неизвестные факты не заполнять
   предположениями.
2. OfficeCLI создаёт новую копию; продолжение правок использует предыдущий
   `result_file_id`. Проверить смысл, поля и вид всех страниц относительно
   источника. Успешный batch/validate не доказывает сохранность оформления.
3. Создать private text-only Skill через native `create_skill`. Description
   должен объяснять, для каких обычных запросов подходит шаблон. Текст содержит
   фактическую карту полей, обязательные и необязательные данные, правила
   сохранения фиксированных частей и финальные проверки. DOCX/base64 туда
   не помещать.
4. После проверки копии и явного согласия пользователя на публикацию вызвать
   `publish_template` с точными ID согласованных Skill и подготовленного File.
   Tool использует текущую native сессию; вспомогательные tasks и отсутствие
   контекста основного сохранённого хода отклоняются.

Tool при необходимости вызывает native обработку оригинала, затем добавляет
тот же File ID в Knowledge, дописывает ссылку на него в инструкцию и сохраняет
для Skill только READ-grants библиотеки. Существующие WRITE-grants библиотеки
не становятся WRITE-grants инструкции. Обработка Knowledge включает штатную
индексацию; отдельного storage-only режима Tool не вводит. Глобальный native
`rag.bypass_embedding_and_retrieval` может отключать embedding, но не является
переключателем одной публикации и здесь не меняется.

`status=published` означает успешный readback текста, активного text-only Skill,
его READ-grants и точной связи File–Knowledge. Receipt содержит сохранённые ID,
версию Skill и ссылку `/api/v1/files/{file_id}/content`. Это ещё не доказывает,
что другой пользователь нашёл инструкцию и правильно заполнил документ.

При `blocked` исправить причину предварительной проверки. При `partial`
сначала прочитать `attempted_step`/`completed_steps` и текущее native состояние:
файл мог уже стать доступен аудитории библиотеки, а Skill ещё остаться private.
Автоматического rollback или повтора нет. После версии-конфликта перечитать
Skill и согласовать актуальную инструкцию; не затирать чужие изменения.

## Читатель: обнаружение и заполнение

В обычном UI native function calling должен быть включён; у модели разрешены
`capabilities.builtin_tools` и `builtinTools.skills`. OpenWebUI автоматически
включает ID, name и description всех активных readable Skills в
`available_skills`, затем предоставляет `view_skill`. Явный выбор Skill,
его model binding или повторная загрузка DOCX для этого не требуются.
API-запрос без native UI session metadata не эквивалентен этому маршруту;
явный `tools`, включая `tools: []`, отключает штатное разрешение builtin tools.

Получив обычное описание задачи, агент выбирает подходящий Skill, читает его,
собирает недостающие данные и передаёт фиксированному Terra worker точный
исходный File ID, полный прочитанный текст Skill без сокращений, включая карту
полей и exact paths, все факты и ограничения. ID/version Skill включаются,
только если фактически получены. На затронутой границе
проверяется полнота переданного контекста, включая результаты инструментов;
один удачный вызов worker этого не доказывает.

OfficeCLI скачивает оригинальные байты через native Files content endpoint с
сессией вызывающего пользователя. Knowledge READ даёт этот доступ; извлечённый
текст Knowledge не заменяет оригинальный DOCX. Worker заполняет новую копию,
проверяет её и возвращает native `result_file_id` и скачиваемый файл.

## Одинаковый текст и обслуживание оригиналов

У старых Word FORMTEXT обновление полей может восстановить служебные defaults
вместо заполненных значений. Это проверяется на конкретном шаблоне, а не по
успешному XML validate. Для проверенного случая штатный `w:fldLock=true` только
на begin-полях с `ffData` фиксирует готовый экземпляр; исходный шаблон, defaults,
стили, закладки и поля PAGE сохраняются. Карту и проверенную операцию хранить в
Skill конкретного шаблона. Не требовать от worker отсутствующий Word: вернуть
созданный файл с реальным статусом проверки; совместимый Word проверить отдельно
при квалификации. Фиксация полей не является парольной защитой документа.

Native Knowledge отвергает разные File ID с одинаковым хешем извлечённого
текста в одной коллекции. Изменение только Word field metadata или оформления
не делает текст уникальным. Повторная индексация того же File ID допускается.
При таком отказе File может сохранить оригинал и извлечённый текст, но получить
`data.status=failed`, duplicate-content error и пустой `hash`; связь с Knowledge
ещё не создана. Общий HTTP 400 сам по себе не устанавливает эту причину.

Проверить сохранённую ошибку, точное членство в KB и равенство извлечённого
текста/его хеша без публикации частного содержания. Для столкновения с устаревшим
репетиционным оригиналом владелец решает, убрать ли его членство или использовать
другую чистую библиотеку. Не менять текст ради обхода dedup.

Только после решения владельца штатный remove endpoint с
`delete_file=false` снимает связь и векторы библиотеки, сохраняя оригинал:
`POST /api/v1/knowledge/{knowledge_id}/file/remove?delete_file=false`, тело
`{"file_id":"<obsolete_file_id>"}`. Проверить readback членства и сохранность
оригинала до нового запуска публикации. Default удаления зависит от
`ENABLE_KNOWLEDGE_FILE_RETENTION`; не полагаться на него. Удаление или замена
оригинала может сломать File ID, записанный в Skill; жизненный цикл обеих
native сущностей требует согласованного решения владельца.

## Приёмка, диагностика и обновление

На новом выпуске проверить один согласованный документ через обычный UI:

- Автор подготовил проверенную копию и явно опубликовал точные ID; readback
  подтверждает инструкцию, версию, grants и членство оригинала.
- Сотрудник получает тот же оригинал с совпадающим SHA-256, но не получает
  publishing Tool или WRITE на библиотеку и опубликованную инструкцию.
  При `user:*` READ любой authenticated сотрудник является разрешённым читателем;
  отрицательная проверка чтения использует неавторизованный запрос. Пользователь
  вне разрешённой группы проверяется отдельно на ограниченной QA-библиотеке
  либо при выбранной групповой аудитории постоянной библиотеки.
- Читатель задаёт общий запрос без Skill ID, mentions, binding или вложенного
  оригинала. Подтверждены manifest, `view_skill`, сбор данных, фактическая передача
  полного задания worker и использование OfficeCLI исходного File ID.
- Финальный результат скачан, сопоставлен с источником по содержанию и
  оформлению; оригинал неизменён, отсутствуют незаполненные обязательные поля.

Для ограниченной диагностики использовать существующий
[final-request debugger](../../deploy/openwebui-patches/provider-context-v0.12.2/README.md):
один saved chat, TTL/лимит запросов, только необходимые child/task scopes.
Сверять фактические инструкции, историю, tools/results, изображения и итоговую
модель после alias resolution. Отключить capture после воспроизведения и
подтвердить status; завершение наблюдателя не означает завершения модели.
Тела capture могут содержать частные документы: хранить вне Git, в публичную
поставку выносить только безопасные выводы и идентичности артефактов.

Перед обновлением сохранить текущие source, Valves, grants и версии Skills;
обновлять существующих владельцев без дублирующих Tools/регистров. После смены
runtime перепроверить затронутые контракты Skill/CAS, Knowledge/pagination,
Files/ACL, native discovery и worker context. Компонентные HTTP-тесты проверяют
поведение адаптера; они не доказывают native ACL или качество DOCX. Новую версию
не объявлять принятой до повторения применимых пользовательских проверок.
