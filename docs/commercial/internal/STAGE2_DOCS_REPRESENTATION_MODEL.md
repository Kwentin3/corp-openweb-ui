# Правила ведения коммерческой документации

Дата: 27 сентября 2026 года.
Назначение: понятная навигация, история отдельных поставок и отсутствие параллельных расчётов.

## Оглавление и отчёт — разные документы

`docs/commercial/README.md` — постоянное оглавление всех поставок. В нём
находятся даты, состав, ссылки и назначение документов, но нет собственного
расчёта часов. Следующие этапы добавляются новыми строками; README не служит
отчётом для акта и не получает версии `README2`.

Каждый самостоятельный набор предъявляемых работ описывается в файле
`COMPLETED_WORK_YYYY-MM-DD_<СОСТАВ>.md`. Дата обозначает дату отчёта,
а не автоматически начало или конец периода работ. Суффикс кратко обозначает
функции или этап; разные поставки одной даты различаются суффиксом.
Не нужен отдельный сводный отчёт на каждый PR: один документ может объединять
несколько функций или один этап большой функции.

## Разделение читателей и статусов

Заказчику нужны результат, объём, ограничения и переход к подтверждениям.
Подробные технические отчёты, инструкции эксплуатации и необработанные
доказательства не переносятся целиком в коммерческую сводку.
Внутренние проверки оснований и архив отделены от основного маршрута.

Сведения о выполнении, инженерной оценке, согласовании, приёмке и оплате
не смешиваются. Публикация документа или слияние PR не меняют остальные статусы.
Реквизиты отсутствующих поручений, согласований и табеля не выдумываются.
Исправление дефекта не объявляется отдельно оплачиваемым только потому,
что оно выполнено после первоначального выпуска.

## Редактура, новая поставка и исправление истории

1. До использования отчёта в подписанном акте черновик можно уточнять в Git,
   отмечая основание и дату изменения состава или оценки. Подробные расчёты,
   сводка и исключения должны оставаться согласованными между собой.
2. Новый предъявляемый объём, включая отдельный этап или последующий рефакторинг,
   получает новый датированный отчёт и строку в оглавлении. Он ссылается
   на исходную поставку и отделяет новые часы от уже учтённых. Прежний отчёт
   не превращается в описание следующего этапа.
3. После использования отчёта в подписанном акте сохраняют сам документ
   и связанные обоснования как историю. Необходимое уточнение оформляют
   отдельным датированным документом со ссылкой на зафиксированную исходную
   версию, основанием и явным описанием отличий. Прежнюю ссылку не заменяют.
4. Для акта указывают конкретный датированный файл, полный SHA коммита
   и выбранные позиции. Дата в имени не делает файл неизменяемым: это
   обеспечивает ссылка `blob/<полный SHA>/...`, а не `main` или README.
   Относительные ссылки на подробные отчёты открываются из того же коммита;
   для материалов из других репозиториев при необходимости фиксируют их версию отдельно.
5. Одно изменение может иметь несколько ссылок на PR, а один PR — обслуживать
   несколько позиций. Это не основание повторно начислять часы. Старые оценки
   не пересчитывают задним числом, а уточнение не объявляют новой работой.
6. Новые технические проверки оформляют в `docs/reports/YYYY-MM-DD/`;
   рабочие ограничения и инструкции остаются в инженерных документах.
7. После перемещения документа оставляют на прежнем адресе короткий указатель.
   Указатель ведёт на тот же предмет, а не на «последний отчёт», и не содержит
   альтернативной часовой карты.

## Сохранение прежних источников

Два прежних файла с маркером `150K` сохранены в `archive/` без изменения
содержимого; их названия являются историческими, а не текущей ценой.
Исходные полные план, handoff и модель документации доступны по постоянным
ссылкам из архива. Новая навигация не меняет их прежних формулировок.

Исторические статусы отражают дату источника и не считаются автоматически
актуальными. [Инженерный контекст](../../stage2/CONTEXT_INDEX.md),
[backlog](../../stage2/ENGINEERING_BACKLOG.md) и
[приёмочная матрица](../../stage2/acceptance/ACCEPTANCE_MATRIX.md)
сохраняют свои роли. PRD описывает намерения продукта, но не заменяет
согласованный состав конкретной поставки.

## Что не публикуем

В GitHub не включаем ставку, денежные суммы, графики платежей, секреты,
провайдерские ключи, пользовательские документы и сырые приватные логи.
Допустимая граница ранее оплаченной работы указывается только для исключения
повторного предъявления и с обозначением источника сведений, без платёжных
реквизитов. Условия оплаты и окончательный расчёт находятся во внешних документах.

Этот рефайн касается только документации: он не меняет код, API, конфигурацию,
CI, ресурсы сервера или работающую установку.
