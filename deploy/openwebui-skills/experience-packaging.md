# Оформить опыт для повторного применения

Собери из рабочего диалога и фактических источников небольшой пригодный к повторению пакет.
Это может быть исследование, работа с API, эксплуатация, обработка данных или разработка;
код нужен только там, где уже полезен. Сохраняй принятый смысл, а не всю переписку.
Подготовку корпоративного DOCX-шаблона ведёт существующий `corporate-template-authoring`.

## When to Use

Пользователь просит «оформим наш опыт как skill», «сохрани этот процесс»,
«сделай из нашей работы повторяемую инструкцию» или доработать существующий Skill.
Сам по себе успешный результат, новый файл или ошибка не требуют упаковки.

## Prerequisites

Нужны доступные источники опыта и права на выбранное место сохранения.
Для Workspace — native Skills tools; для исполняемого пакета — выбранный доступный
Terminal с проверенными владельцем исполнения, лимитами и адресной остановкой.
Проверь фактический набор tools; недоступность записи не подменяй заявлением о сохранении.
Не запрашивай секреты в переписке: укажи штатный способ предоставления доступа.

## How to Run

Сначала найди подходящий существующий Skill через доступный список и `view_skill`.
Сохрани разовый результат как артефакт; повторяемую детерминированную операцию —
как скрипт; Skill нужен, когда повторное применение требует выбора, правил и контекста.
Не создавай новый Skill рядом с владельцем того же процесса без необходимости.
Просьба упаковать опыт разрешает личное сохранение в пределах задачи.
Уже принятые решения повторно не согласовывай.

## Quick Reference

- `view_skill`, `read_skill_file`: прочитать существующие инструкции и ресурсы; продолжить чтение при `next_offset`.
- `create_skill`: новый private Workspace Skill, `content` содержит полный `SKILL.md`, `files` — UTF-8 supporting files.
- `update_skill_files`: выбранные `put`/`move`/`delete`, новая native версия без перезаписи остальных файлов.
- `write_file`, `run_command`: материализация и проверка Terminal-пакета в подтверждённой среде.
- Workspace editor/API: отдельные native name/description, права, history/diff и возврат к версии.

## Procedure

1. Кратко назови повторяемую задачу, ожидаемый результат и состав пакета.
   Прочти все названные источники и нужные фактические файлы, не только последний ответ.
   Отдели подтверждённые правила и результат от гипотез, неудачных попыток и неизвестного.
   Неудачу включай лишь как полезное ограничение с причиной и областью применимости.
   Каждое влияющее на результат правило сверь с конкретным соглашением или источником.
   Сохраняй его область и условия; не добавляй меняющую результат нормализацию без основания.
   Безобидный выбор оформления допустим; предположение, меняющее смысл или состав результата, требует решения.
2. Собери известное сам, технические предположения проверь доступными средствами.
   Если отсутствует существенное пользовательское решение, задай короткий вопрос с последствиями
   вариантов: например, остановиться при устаревшем источнике или разрешить его использование.
   Не угадывай бизнес-правило, аудиторию, допустимый побочный эффект или критерий результата.
   Независимую подготовку продолжай; до ответа сохраняй только явно обозначенный личный черновик.
   Необязательную неопределённость запиши ограничением, не превращая её в блокирующий вопрос.
3. Выбери минимальный состав и одного владельца каждого элемента:
   Workspace — инструкции и небольшие текстовые справки; Terminal — исполняемый код и его ресурсы;
   native Files/Knowledge — исходные материалы, шаблоны и бинарные результаты по существующим правилам.
   Workspace supporting files виртуальны: они не устанавливаются и не запускаются автоматически.
   Для кодового workflow каноничен filesystem Terminal Skill; не создавай вторую копию его правил
   в Workspace и не обещай синхронизацию. Sharing Workspace не устанавливает код другим людям.
4. Запиши только то, что нужно следующему запуску: назначение и триггеры, входы/выходы,
   принятые правила, доступные tools, зависимости, порядок действий, существенные ошибки и проверку.
   Используй native структуру: When to Use → Prerequisites → How to Run → Quick Reference →
   Procedure → Pitfalls → Verification. Крупный код вынеси в `scripts/`, справки в `references/`,
   шаблоны в `templates/`, бинарные ресурсы в `assets/`, лишь когда они реально нужны.
   Не копируй секреты, полную историю, личные данные или глобальные правила чужих владельцев.
5. Подготовь конкретные frontmatter `name` и `description`: name lowercase-hyphenated, до 64
   символов; description до 1024 символов, с точными триггерами и точкой в конце. Посчитай длину.
   Запиши description как JSON-совместимую строку в двойных кавычках с экранированием.
   Если доступен YAML-парсер, проверь разбор frontmatter и совпадение полученного description.
   Не делай описание универсальным. `platforms` добавляй только для зависимости от ОС.
   Native Workspace `id` — уникальный slug, `name` — отображаемое название, `description` —
   отдельное поле маршрутизации. Tags не заменяют описание; произвольные registry-поля не вводи.
6. Сохрани выбранным штатным путём:
   - Workspace: `create_skill` либо сначала `view_skill`, затем `update_skill_files` с точечными
     операциями. Native CAS использует прочитанную версию; при `version_conflict` перечитай и
     перенеси изменение без затирания чужой работы. Через editor/API сохраняй `expected_version_id`.
     Обновление frontmatter не обновляет отдельные native name/description: при изменении
     смысла исправь их через разрешённый editor/API и перечитай отдельно от `SKILL.md`.
     `view_skill` не возвращает native description и не подтверждает проверку этого поля.
   - Terminal: подтверди user home и существующий discovery root, проверь одноимённые Skills
     во избежание затенения. Через `write_file` сохрани `SKILL.md` рядом с кодом и ресурсами.
     В следующих запусках используй `directory` из `view_skill` и явные пути, а не прежний `cd`.
     Сохрани полный проверенный выпуск: существующий Git, если он уже владелец, или архив
     с точным составом/хэшами. Fingerprint инструкции не закрепляет весь код и ресурсы.
7. Отдели изменяемое состояние от распространяемого пакета: настройки пользователя, историю,
   checkpoint и результаты храни в явно указанной рабочей папке соответствующего владельца.
   Зафиксируй нужные права чтения/записи; проверь их после реального сохранения, в том числе
   атомарного. `Permission denied` не обходи расширением ACL. Неизвестный исход записи перечитай
   перед повтором; не обещай восстановление только потому, что данные лежат на volume.
8. Для выполнения через `run_command` заранее определи срок, пределы, наблюдение и адресную
   остановку. `wait` не является сроком жизни процесса. После timeout/stop проверь завершение
   принадлежащей запуску работы до повтора. Процесс user+chat не переносится в новый чат по ID.
   Обычный запуск использует принятый выпуск; не переписывай код молча «по пути».
   Исправление правила или ошибки — отдельная адресная доработка с проверкой новой версии.
9. Перечитай сохранённый пакет и metadata. Коротко укажи основание/дату проверки, принятый
   выпуск и ограничения; отдельная обязательная система manifest/status не нужна.
   Личный черновик явно назови черновиком в описании и теле: native active не означает «проверен».
   Не предлагай незавершённый пакет для обычного применения. После успешной проверки уточни
   описание; shared означает доступ согласованной аудитории через существующие права.
   Не расширяй аудиторию по умолчанию и не вводи дополнительное согласование уже разрешённого.
10. При обновлении сохрани прежний принятый выпуск. Workspace откатывай через native history
    с проверкой текущей версии; Terminal — полным сохранённым выпуском. До возврата проверь
    совместимость с текущим состоянием: откат кода не откатывает накопленные данные.
    В ответе дай название/ID или путь, пример вызова, место ресурсов и состояния, что проверено
    и оставшийся существенный шаг. Различай «сохранён», «доступен» и «проверен».

## Pitfalls

Модельное «готово», успешный API, exit code и существование файла не доказывают результат.
Native Terminal resource list ограничен глубиной и количеством; проверь полный нужный состав.
Недоступный источник или непроверенный шаг укажи явно; не повышай гипотезу до принятого правила.
Ссылка или ZIP в чате не выдаёт права коллегам; личное состояние не входит в общий пакет.

## Verification

Проверь смысл на одном представительном входе и сверяй результат и пропуски с источником:
для исследовательской инструкции — выводы/основания; для API — фактический ответ и побочные
эффекты; для кода — реальный выход и повтор; для файлов — содержимое и открытие/скачивание.
Для каждого существенного исключения или инварианта составь и фактически разбери контрпример.
Сверь его результат с принятыми правилами; противоречия исправь до заявления готовности.
Где сущности и строки различаются, считай их отдельно и явно указывай единицу подсчёта.
Затем в новом чате с нужными доступами проверь обычную формулировку запроса, чтение пакета,
ресурсов и прежнего состояния без старой переписки; близкий посторонний запрос не должен
навязывать этот процесс. Для shared проверь доступ целевой аудитории и изоляцию личного.
Выполняй только разрешённые проверки; непроведённую приёмку называй оставшимся шагом.
